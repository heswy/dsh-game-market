## 1. 包格式：`html-v1` 与 `asset-zip-v2` 联合类型

### 1.1 联合类型与判定顺序

```ts
type PackageFormat = 'html-v1' | 'asset-zip-v2';

interface PackageRef {
  format: PackageFormat;   // 缺省（V1 索引/旧记录）等价于 'html-v1'
  url: string;             // 文件名必须与 format 匹配（见 1.2）
  sha256: string;          // 外层摘要：HTML 文件本身 / ZIP 文件本身
  size: number;            // 外层字节数
  releasedAt: string;
}
```

判定顺序（Host 安装入口 MUST 按此顺序，任一步失败即拒绝，不进入下一步）：

1. 索引/请求声明的 `format`；缺省视为 `html-v1`。
2. URL 末段文件名必须与 `format` 匹配：`html-v1 → <id>-<version>.html`；`asset-zip-v2 → <id>-<version>.dshgame.zip`。
3. `Content-Type` 与本地安装入口分离（§14：ZIP 不接受 raw `text/html` 上传路径）。
4. 魔数校验：`asset-zip-v2` MUST 以 `PK\x03\x04` 开头（空 ZIP 亦须为 `PK\x05\x06`），否则 `GM-4270`。
5. 只有校验通过后才按对应管线处理：`html-v1` 走 V1 `validatePackageHtml`；`asset-zip-v2` 走 §3/§4 管线。

`format` 与 `version` 不得互相推导：**不能**用版本号猜格式，也**不能**用格式替换同一版本（§5.4）。

### 1.2 包文件名与扩展名

| format | 文件名 | 扩展名常量 | 说明 |
|---|---|---|---|
| `html-v1` | `<id>-<version>.html` | `PACKAGE_EXTENSION = '.html'`（沿用） | V1 不变 |
| `asset-zip-v2` | `<id>-<version>.dshgame.zip` | `PACKAGE_ZIP_EXTENSION = '.dshgame.zip'`（新增） | 双扩展名是**刻意的**：`.dshgame.zip` 明确"这是本平台的游戏包"，且不与普通 `.zip` 混淆；URL 末段校验与 v1 同源 |

`packageFileName(id, version)`（`manifest.js`，沿用 v1）不得修改；新增 `zipPackageFileName(id, version)`。
索引条目 URL 末段的比较 MUST 用 `endsWith('/' + expectedFileName)` 的**精确段比较**（不得用子串包含）。

### 1.3 `asset-zip-v2` 包结构（冻结）

```text
orbit-courier-1.0.0.dshgame.zip
├── dsh-package.json        # 描述符（formatVersion: 2），自身不列入 files
├── game.json               # 唯一权威 manifest（v1 语义）
├── index.html              # entry（示例；实际由描述符 entry 指定）
├── scripts/main.js
├── styles/game.css
├── assets/ship.webp
├── assets/pickup.ogg
└── levels/level-01.json
```

MUST NOT 出现：嵌套压缩包、安装/构建脚本（`package.json`/`postinstall`）、Node 模块（`.node`/`node_modules/`）、
可执行位、符号链接/硬链接/设备文件、ZIP 之外的容器、任何形式的动态代码下载入口。

> 说明：ZIP 条目**可以**有 Unix mode 位（作者用系统 zip 时会带）；契约按**白名单类型 + 禁止类型位**判定（§4.6），
> 不要求作者剥掉 mode 位，但符号链接位（mode 高 16 位 `0o120000`）与设备/管道/FIFO 位一律拒绝。

### 1.4 `dsh-package.json` 字段级契约

```json
{
  "formatVersion": 2,
  "entry": "index.html",
  "gameManifest": "game.json",
  "files": [
    { "path": "index.html", "size": 1234, "sha256": "<64 lowercase hex>" },
    { "path": "game.json",  "size":  612, "sha256": "<64 lowercase hex>" }
  ]
}
```

| 字段 | 类型 | 必填 | 约束 | 违规码 |
|---|---|---|---|---|
| `formatVersion` | integer | 是 | MUST `=== 2` | `GM-4277`（`E_DESCRIPTOR_INVALID`） |
| `entry` | string | 是 | 规范化相对 POSIX 路径（§4.2）；MUST 出现在 `files[]`；MUST 以 `.html` 结尾 | `GM-4277` / `GM-4273` |
| `gameManifest` | string | 是 | MUST `=== "game.json"`（V1.5 只允许根 `game.json`）；MUST 出现在 `files[]` | `GM-4277` |
| `files` | array | 是 | ≥1、**≤511**（描述符自身占 1 个 ZIP 条目，总条目上限 512，见 §3）；每项 `{path,size,sha256}`；按 `path` 的 **UTF-8 字节序**严格递增；不含描述符自身；不含目录项 | `GM-4277` / `GM-4274` |
| `files[].path` | string | 是 | 同 §4.2 路径规则；大小写敏感 | `GM-4273` |
| `files[].size` | integer | 是 | ≥0；MUST 等于解压后实际字节数（不符 → `GM-4276` CRC/实测不符或 `GM-4278`） | `GM-4278` |
| `files[].sha256` | string | 是 | `^[a-f0-9]{64}$`；MUST 等于解压后实际字节 sha256 | `GM-4278` |
| 未知字段 | any | 否 | 允许 `x-` 前缀；其他未知字段**警告**（`W_DESCRIPTOR_UNKNOWN_FIELD`），不拒绝 | — |

描述符本身：MUST 位于 ZIP 根；大小 ≤ 256 KiB（`LIMITS.descriptorBytes`）；MUST 是 UTF-8 无 BOM 的 JSON 对象；
MUST NOT 列入 `files[]`（避免自引用摘要）—— 其完整性由**外层 ZIP 摘要**与描述符所在字节区间共同绑定。

### 1.5 逐文件清单的语义

1. `files[]` 必须**恰好覆盖** ZIP 中除描述符以外的全部条目：多一个 → `GM-4278`（额外文件）；少一个 → `GM-4278`（缺失文件）。
   条目边界统一按**总条目数**计：ZIP 内条目总数（**含 `dsh-package.json`**）≤512，因此 `files[]` ≤511（§3）。
2. 目录项（以 `/` 结尾且 size=0 的条目）MUST NOT 出现在 ZIP 中（拒绝，`GM-4270`）；目录由解压器按需创建。
3. 清单排序固定（1.4），因此同一内容生成确定性 ZIP：构建两次字节一致（`PACKAGE.md`/CLI 验收项 P03）。
4. `files[]` 是**资源服务的唯一路径来源**（§7.4）：运行时只服务清单内的路径，绝不做目录列举或任意磁盘路径解析。
5. `fileManifestDigest`（安装记录，§6.2）定义：对描述符 `files[]` 数组按**已排序原样**做规范序列化
   `JSON.stringify(files.map(f => ({path:f.path,size:f.size,sha256:f.sha256})))` 后取 sha256（十六进制小写）。
   该摘要与**外层 sha256** 一起写进安装记录，用于回滚比对与资源映射校验。

### 1.6 manifest 权威性与冲突拒绝规则

| 规则 | 内容 | 违规 |
|---|---|---|
| 唯一权威 | `asset-zip-v2` 中 `game.json` 是唯一权威 manifest，字段语义 = V1 `manifest v1`（`manifestVersion:1`） | 缺 `game.json` → `GM-4277`；`game.json` 自身非法 → `GM-4221`/`GM-4228`/`GM-4230–4248`（沿用 v1 码） |
| 禁止双声明 | ZIP 包内**任何**文件出现内嵌 manifest 脚本 `<script type="application/json" id="dsh-game-manifest">` → 直接拒绝 | `GM-4279`（`E_MANIFEST_CONFLICT`） |
| 描述符 vs manifest | `game.json` 的 `id`/`version` MUST 与索引条目、目录名、文件名 `<id>-<version>` 完全一致 | `GM-4095`（沿用 `INSTALL_VERSION_MISMATCH`） |
| entry vs manifest | 描述符 `entry` 指向的文件 MUST 存在且类型白名单允许 | `GM-4278` / `GM-4280` |
| `manifestVersion` | 保持 `1`；`formatVersion`（包封装）= `2`。**两者不得互相替代** | 混用 → `GM-4230`（manifestVersion 非 1）/ `GM-4277` |
| 自包含检查 | `html-v1` 沿用 `checkSelfContained`；`asset-zip-v2` 用 §4.7 的**相对资源白名单**取代"单文件自包含"检查 | `GM-4225`（沿用）/ `GM-4280` |

> 为什么"存在内嵌 manifest 就拒绝"而不是"一致就接受"：双声明会产生两个可被不同代码路径读取的权威，
> 任何"取其一"的实现都会在某个入口退化；确定性拒绝的测试成本最低、攻击面最小。**这是本契约的冻结选择**（§13.1 D-J 已裁决）。

### 1.7 版本规则

1. `formatVersion: 2` 属于**包封装**；游戏语义版本仍是 `game.json.version`（严格 semver 子集，禁止 `+build`）。
2. SDK/Runtime 范围仍是 `game.json.sdkVersion` / `runtimeVersion`（`^1.0.0` 等），与包格式无关；
   平台不得为了运行 `asset-zip-v2` 改变 SDK/Runtime 版本（沿用 V1「禁止自动升降级」）。
3. `html-v1 → asset-zip-v2` **必须升游戏版本**（新版本目录、新索引条目、新 sha256）；
   同 `id` + 同 `version` 的字节**不可变**（§5.4）。
4. ZIP 内 `game.json` 的 `version` MUST 与包文件名、目录名、索引条目一致；不允许"包内版本旧、文件名新"。

### 1.8 本地安装入口（`html-v1` 沿用 + `asset-zip-v2` 新增）

| 入口 | 载体 | 规则 |
|---|---|---|
| `POST /install-local`（沿用） | raw `text/html` ≤20 MiB，`source:'local'` | V1 语义不变：`sha256` 记 `null`、必须二次确认、不做完整性承诺 |
| `POST /install-local`（V1.5 扩展） | raw `application/zip`（或 `application/x-zip-compressed`）≤20 MiB，`?operationId=` | 必须与 HTML 入口分离 `Content-Type` 判定（禁止用换 content-type 绕过限额）；`source:'local'`；记录**实测**外层 sha256（仅用于回滚比对与诊断，**不是**信任锚，UI 仍须二次确认并展示文件名/大小/文件数）；其余走 §4 全套校验 |

- 本地 ZIP 的 `format` 由 `Content-Type` + 魔数判定，**不看文件名**；两者不一致 → `GM-4150`（沿用 `UNSUPPORTED_MEDIA_TYPE`）。
- 本地安装同样受 §3 限额与 §4 路径/归档检查约束；不做"因为是用户自己选的所以放宽"。
- 上传入口的两级限额（宿主接收层 + 应用层）沿用指南 §4.2：MUST 在收到正文前按 `Content-Length` 预判并拒绝超限。
- **已裁决（§13.1 D-N / Q-11）**：接受本地 ZIP（单独 `Content-Type`、≤20 MiB、`source:'local'`、记录实测外层 sha256 但标记为非信任锚、必须二次确认）；不强制作者改走 Release URL。

### 1.9 生成确定性

CLI `pack` 产出的 ZIP MUST 可复现：条目顺序按 `files[]` 排序、固定压缩级别、固定时间戳（构建时间不写入条目 mtime；
或固定为 `1980-01-01 00:00:00`）、不写入作者本机绝对路径与用户名。两次构建字节一致（P03 验收）。

### 1.10 SDK 交付（`asset-zip-v2` 的关键差异，MUST）

`html-v1` 的 SDK 是构建期内联的；ZIP 包**没有**"单文件"这个载体，因此：

1. CLI `pack` MUST 把 `packages/sdk`（与 `SDK_VERSION` 对应）打进包内**一个**清单文件
   （建议 `dsh-sdk.js`，列入 `files[]` 并参与 sha256 校验），由 entry HTML 用**相对** `<script src="dsh-sdk.js">` 加载，
   且早于游戏代码执行。
2. 平台 MUST NOT 在服务时向 entry 或任何资源注入/改写字节：`/entry` 与 `/asset` 返回的就是包内原始字节
   （与清单 sha256 绑定），否则"审核绑定原始字节"失效。
3. ZIP 包内的 SDK 额外暴露 `game.runtime.assetUrl(relativePath)`（§7.3），供游戏按需加载关卡/图片/音频；
   该函数只在实例资源前缀下可用；`html-v1` 游戏调用时返回 `GM-4043`（无资源路由绑定）。
4. SDK 版本协商沿用 v1（`sdkVersion` 范围；`ready` 前 `runtimeVersion` 为 `null`）；
   `pack` MUST 校验 `game.json.sdkVersion` 与内嵌 SDK 版本一致（含范围匹配），禁止"声明 `^1.1.0` 却内嵌 1.0.0"。

| 全包压缩比 | `zipTotalRatio` | ≤ 100:1（`unpacked / outer`） | 实测 |
| 单文件压缩比 | `zipEntryRatio` | ≤ 100:1 | 逐条实测 |
| 路径长度 | `zipPathChars` | ≤ 240 个 Unicode 码点 | 政策检查 |
| 路径深度 | `zipPathDepth` | ≤ 12 段（`/` 分隔，不含文件名占 1 段） | 政策检查 |
| 描述符字节 | `descriptorBytes` | ≤ 256 KiB | 解压描述符时 |
| `game.json` 字节 | `manifestBytes`（沿用） | ≤ 64 KiB | 复用 v1 校验 |
| 支持压缩方法 | — | 仅 `0` Stored、`8` Deflate | 中央目录 + 本地头 |
| 明确不支持 | — | 加密（GP bit0/bit6）、多卷、嵌套压缩包、符号链接、硬链接、设备/FIFO、ZIP64、数据描述符之外的未知特性位 | 见 §4.4 |
| 解压总时限 | `zipExtractMs` | 60 s（挂钟） | 安装 job |
| 解压内存预算 | `zipChunkBytes` | 64 KiB/块；单条流不整文件入内存 | 实现 |
| staging 磁盘预算 | — | `zipOuterBytes + zipUnpackedBytes`（≤120 MiB） | 安装前预检 |

规则：

0. **描述符计入总条目数**（Lead 裁决，统一边界）：限额的目的是约束解压器必须处理的条目数，而 `dsh-package.json` 本身就是
   一个中央目录条目。因此**总条目（含描述符）≤512**、`files[]` ≤511；不允许出现"512 + 1"的实现歧义。
   `files[]` 长度 512 或 ZIP 条目总数 513 都必须被拒绝（`GM-4272`）。
1. **预检与实际解压都检查**：预检用于尽早失败与给出可理解错误，实测是权威；两者不一致 → `GM-4275` 或 `GM-4272`。
2. 任一限额超出 → `GM-4272`（`E_ZIP_LIMIT_EXCEEDED`），错误 `details` 只允许带 `{limit, actual, kind}`，不带作者内容或绝对路径。
3. 限额只在 `packages/shared` 与 `packages/host/src/zip.js` 定义一次；CLI `validate`/`pack` 复用同一常量与校验器，禁止各处硬编码。
4. 上传入口的两级限额（宿主接收层 + 应用层）沿用指南 §4.2：MUST 在接到流之前就判断 `Content-Length`，
   超限直接 `GM-4135`；不允许"收完再判断"，也不允许通过换 `Content-Type` 绕过。

## 4. 路径与归档检查规则

### 4.1 检查顺序（MUST，任何一步失败即中止，不产生落盘副作用）

1. 外层大小/文件名/魔数（§1.1）。
2. 中央目录结构合法性（EOCD、条目数、偏移）→ `GM-4270`。
3. 逐条读取中央目录元数据（`decodeStrings:false`，字节原样）→ ZIP64/加密/多卷/方法位判定（§4.4）。
4. 逐条**路径规范化与拒绝**（§4.2）→ 先在内存建立 `Map<normalizedPath, entry>`。
5. **冲突检查**（§4.3）全部完成后再创建任何文件（"先检查冲突，再创建文件"）。
6. 描述符存在性/大小/JSON/schema（§1.4）→ `GM-4277`。
7. 清单与实际条目集合比对（缺失/额外/大小/sha）→ `GM-4278`。
8. 逐条解压 + 实测字节数 + CRC-32 + sha256（§4.5）→ `GM-4276`/`GM-4278`。
9. 本地头与中央目录一致性（§4.4）→ `GM-4275`。
10. `game.json` 校验（v1 语义）+ `entry` 存在性 + 类型白名单/内容扫描（§4.6/§4.7）→ `GM-4221`/`GM-4225`/`GM-4280`。
11. 全部通过后才把 `staging/<jobId>/` 原子提升为 `packages/<id>/<version>/`（沿用 V1 §6.3 步 10）。

### 4.2 路径规范化与拒绝列表

规范化算法（MUST 逐条实现，测试按此命名）：

1. 以**字节**读取条目名（`decodeStrings:false`），按 UTF-8 严格解码；非法 UTF-8 → 拒绝 `GM-4273`。
2. 拒绝空名、拒绝含 `\u0000`（NUL）、拒绝含控制字符（`[\u0000-\u001F\u007F]`）。
3. 拒绝任何反斜杠 `\`（ZIP 规范用 `/`；`\` 是 Windows 路径穿越的常见载体）→ `GM-4273`。
4. 拒绝绝对路径：首字符 `/`、`\\`、盘符 `^[A-Za-z]:`、UNC（`//` 开头）。
5. 按 `/` 切分；拒绝任何空段（`//`）、`.`、`..` 段。
6. 拒绝段尾以空格或 `.` 结尾（Windows 归一会把它们吞掉，制造同名/越界歧义）。
7. 重新拼接为相对 POSIX 路径；断言拼接结果不含 `..` 段且不以 `/` 开头（**二次防御**，防实现回归）。
8. 断言路径长度 ≤240 码点、深度 ≤12。
9. 断言路径类型在白名单内（§4.6）且不含保留名（`dsh-package.json` 之外的描述符同名、`con`/`nul`/`aux`/`prn`/`com1`… 等 Windows 保留名一律拒绝）。

### 4.3 冲突与歧义检查（在创建文件之前完成）

| 检查 | 规则 | 错误 |
|---|---|---|
| 完全重复 | 规范化后同一路径出现两次 | `GM-4274` |
| 大小写折叠冲突 | ASCII 大小写折叠后相同（HFS+/Windows 上会互相覆盖） | `GM-4274` |
| Unicode 规范化冲突 | NFC 归一后相同（实测命名冲突样例：`café.txt` vs `cafe\u0301.txt`） | `GM-4274` |
| 目录/文件同名 | `a` 与 `a/b` 同时作为条目 → 一个要当文件、一个要当目录 | `GM-4274` |
| 大小写/归一化折叠后的目录-文件冲突 | 上述规则的组合投影 | `GM-4274` |
| 描述符重名 | 除根 `dsh-package.json` 外任何路径不得再叫这个名字 | `GM-4277` |

判定用**规范化后的路径**，判定必须在任何 `mkdir`/`writeFile` 之前完成（测试须断言失败时 `staging/` 为空目录）。

### 4.4 归档特性：支持 / 拒绝

| 特性 | 判定依据 | 处置 |
|---|---|---|
| Stored (0) / Deflate (8) | `compressionMethod`（中央目录） | 允许 |
| 其他方法（1/6/9/12/14/93/95/98…） | 同上 | `GM-4271` |
| 加密（传统/strong） | `generalPurposeBitFlag & 0x1` 或 `& 0x40`；yauzl 对 strong 直接报错 | `GM-4271`（**先于** `openReadStream` 判定；不得尝试解密） |
| 多卷 / 分卷 | EOCD `diskNumber`；yauzl 报 `multi-disk zip files are not supported` | `GM-4271` |
| ZIP64 | 中央目录 extra field id `0x0001`、`versionNeededToExtract >= 45`、或 EOCD 哨兵值（`0xFFFF`/`0xFFFFFFFF`） | `GM-4271`（yauzl 本身**支持** ZIP64，因此必须显式拒绝）。`M1 落地前置（归属 M1/A03）`：本轮未构造出真实 ZIP64 样本，M1 必须补 fixture 并断言拒绝 |
| 数据描述符（GP bit3） | 允许（很多构建器默认），但**实测值**以解压为准，中央目录不得被当作权威大小 | 允许 |
| 嵌套压缩包 | 条目名以 `.zip/.dshgame.zip/.gz/.tar` 等结尾 **或** 魔数为 `PK\x03\x04` | `GM-4271`（按内容魔数判定，不只按扩展名） |
| 符号链接/硬链接/设备/FIFO | `externalFileAttributes` 高 16 位 Unix mode：`S_IFLNK(0o120000)`/`S_IFCHR`/`S_IFBLK`/`S_IFIFO`/`S_IFSOCK` | `GM-4271`（实测 yauzl 能给出该字段；普通文件 `0100644`/`0600`/`0` 均允许） |
| 本地头与中央目录不一致 | 见下 | `GM-4275` |

**本地头 vs 中央目录一致性（MUST 显式实现）**：实测 `yauzl` **不会**报告二者不一致
（它用中央目录做权威、用本地头定位数据，并用 `validateEntrySizes` 校验大小）。
因此 M1 的 `zip.js` MUST 自行比较每一项：
`本地头签名(0x04034b50)`、`本地头 fileName 字节`（与中央目录逐字节相同）、`generalPurposeBitFlag`（除 bit3 数据描述符差异）、
`compressionMethod`、以及**实际读取到的压缩字节区间**（= `entry.compressedSize`，若不符 → `GM-4275`）。
这是本契约对所选读取器**已知局限**的补偿措施（记录于 `raw/brand/b1-zip-reader-eval.json#readerLimitations`）。

### 4.5 摘要与完整性

1. 外层：下载/读取时**边读边算** sha256，与索引条目 `sha256` 比较（`GM-5015`），大小与 `size` 比较（`GM-4135`/`GM-5015`）。
2. 描述符：JSON 解析 + schema（§1.4）→ `GM-4277`；`formatVersion !== 2` → `GM-4277`。
3. 每个条目：解压后实测字节数 MUST 等于 `files[].size`（`GM-4278`）；
   实测 sha256 MUST 等于 `files[].sha256`（`GM-4278`）；
   实测 CRC-32 MUST 等于中央目录 `crc32`（`GM-4276`）。
4. CRC-32 实现：优先 `node:zlib.crc32`（Node ≥ 22.2 / ≥ 20.15）；不可用时使用表驱动 CRC-32/ISO-HDLC，
   自测向量 `crc32("123456789") === 0xCBF43926`（实测本机 Node v24.14.0 两者均可用）。
   **落点必须是 `packages/host/src/zip.js`**：`packages/shared/**` 禁止 import Node 内建模块（`contracts.js` 规则 2），
   shared 只承载路径/描述符/清单等纯 JS 政策。
5. 不信任中央目录宣称值：`uncompressedSize` 只用于预检与 `validateEntrySizes` 交叉校验，权威是实测值。
6. 清单缺失/额外、描述符缺失、`game.json` 缺失 → `GM-4278`/`GM-4277`；entry 缺失 → `GM-4043`/`GM-4278`。

### 4.6 类型白名单（静态前端资源）

| 类别 | 允许的扩展名 | 说明 |
|---|---|---|
| 文档 | `.html` | 仅 `entry` 与包内页面；不得含 `<base>`、外部导航、`<iframe>` |
| 脚本 | `.js` `.mjs` | 仅包内相对 import；禁止 `import()` 远程 URL、`eval`/`new Function`、`serviceWorker` |
| 样式 | `.css` | 禁止 `@import` 外部、`url()` 指向包外 |
| 图片 | `.png` `.webp` `.jpeg` `.jpg` `.gif` `.svg` | SVG 按图片处理（`nosniff` + `image/svg+xml`），不得当 HTML 提供 |
| 音频 | `.ogg` `.mp3` `.wav` `.m4a` | 失败需可降级 |
| 字体 | `.woff2` `.woff` | 仅本地文件 |
| 数据 | `.json` `.txt` `.csv` | 关卡/配置 |
| 描述符 | `dsh-package.json`（仅根部） | 不参与资源服务 |
| manifest | `game.json`（仅根部） | 不参与资源服务（Host 读取，不向 iframe 暴露） |

不在白名单 → `GM-4280`。V1.5 **不支持** WASM、Worker、外部网络、`<iframe>`、`allow-same-origin`（§14）；
包内**相对同源**读取是允许的（§4.7 Q-6 裁决），由 `connect-src` 强约束。
类型判定 MUST 用扩展名 + 内容魔数双重判定（如 `.js` 内容为 `PK` → 按嵌套归档拒绝）。

### 4.7 内容扫描（第二道防线，不构成证明）

在 `entry` 与所有 `.html` 上 MUST 拒绝：`<base>`、`<iframe>`、外部 `src`/`href`（`http:`/`https:`/`//host/…`）、
`@import` 外部、`eval(`/`new Function(`、`serviceWorker`、`window.open`。

**包内相对读取（Q-6 已裁决：允许）**：

| 允许 | 拒绝 |
|---|---|
| 同源相对 POSIX 路径的 `fetch()`/`XMLHttpRequest`/ESM `import()`，形如 `./x`、`x/y`、`../x`（规范化后仍在包内、不以 `/` 开头） | 任何带 scheme 或 authority 的 URL：`http:`、`https:`、协议相对 `//host/…`、`blob:`、`ws:`/`wss:`；`data:` 仅限已白名单的图片/音频位置，**不得**用于 fetch |
| `<script src>`/`<link href>`/`<img src>`/`<audio src>` 的包内相对路径（§4.6 白名单类型） | 绝对路径 `/…`、远程地址、重定向到包外 |

- **安全边界由运行时 CSP 强制执行，而不是静态扫描**：入口文档 `connect-src http://127.0.0.1:<resourcePort>`（§7.5）
  才是「只能读本实例资源」的权威约束；它**按 origin 匹配**（同 origin 的绝对 URL 也放行、其他 origin 一律阻断），
  静态扫描**不需要、也无法**通过区分「相对 vs 绝对」来保证安全。
- 因此下表的「拒绝」列是 **validator 的创作期规则**：目的是可移植（不假设资源 origin 的绝对地址）、可静态审计、
  作者得到更早的错误；**不得**把它写成安全保证。（子文档自导航是另一类边界，见 §7.5.1。）
- 上表「拒绝」项仍作为**纵深防御**保留在 validator 中（能给作者更早、更清楚的错误），但它不是安全证明。
- 这条规则直接支撑 V1.5 头号交付物：指南 §4.1 的包结构示例含 `levels/level-01.json`，§4.5 要求新内置游戏
  「一份关卡 JSON、一个本地音效必须实际加载」；S-A1 已实测严格 CSP 下 `fetch('./levels/level-01.json')` 两次 200 并解析成功
  （`signature=level-01:5:1200`，见 `docs/verification/v1.5/resources.md`）。
- M1 validator 用例（A03 矩阵）：**允许**——`fetch('./levels/level-01.json')`、`fetch('scripts/x.json')`、ESM `import('./mod.js')`；
  **拒绝**——`fetch('https://example.com/x.json')`、`fetch('//example.com/x.json')`、`fetch('/abs.json')`、`fetch('data:application/json,…')`。

`asset-zip-v2` 额外禁止（裁决 3，从严；错误码 `GM-4283`，见 §7.5）：内联 `<script>` 块、内联 `<style>` 块、
内联事件处理器属性（`on*=`）、`javascript:` URL。三类 MUST 各有 validator 用例（A03 拒绝矩阵），且不得产出版本目录。
`html-v1` 保持现状（单文件允许内联，CSP 保留 `'unsafe-inline'`），不回归。

> 指南 §4.2 明确：**运行时 CSP 与服务器准入是最后防线，静态正则扫描不能作为"无网络/无恶意行为"的证明**。
> 因此 §4.7 只是纵深防御之一，验收仍须由 A03/A06 的真实浏览器用例覆盖。

## 5. 两代索引（Registry v1 + v2 并存）

### 5.1 v1 索引（沿用，只含 HTML）

- 路径/文件名不变：`/registry/games.json`，`registryVersion: 1`（`registry.js#REGISTRY_VERSION`），schema 与校验器 `validateRegistry` **不修改**。
- v1 投影 MUST 只包含 `format === 'html-v1'` 的 release；生成器必须显式过滤，而不是"默认没有 format 就当 HTML"。
- V1.5 Host 读取 v1 索引时：若任一条目出现 `package.format === 'asset-zip-v2'` → **整份拒绝**（`E_REGISTRY_INVALID` → `GM-5032`），
  回退缓存/种子；理由：这说明内容仓库投影逻辑出错，而旧客户端会把 ZIP 条目当 HTML 下载并整份校验失败（指南 §4.4）。
- 旧客户端行为不变：v1.2 客户端继续只读 v1 索引，继续可玩已安装游戏。

### 5.2 v2 索引（新增）

路径：`/registry/v2/games.json`；同一内容仓库、同一审核源、同一 PR 生成。

```ts
interface RegistryV2 {
  registryVersion: 2;          // MUST === 2
  generatedAt: string;         // ISO-8601 Z（取源记录中最大固定更新时间，非构建时间）
  truncated?: boolean;
  games: RegistryGameV2[];     // ≤ 500 条
}

interface RegistryGameV2 {          // 在 V1 RegistryGame 基础上：
  // ...沿用：id/name/version/description/author/categories/tags?/capabilities/
  //          sdkVersion/runtimeVersion/preferredTheme?/icon?/cover/screenshots?/
  //          homepage?/repository?/license?/changelog?/featured?/quickPlay?/
  //          publishedAt/updatedAt
  package: {
    format: 'html-v1' | 'asset-zip-v2';   // v2 索引中 MUST 显式声明，无缺省
    url: string;                          // 末段文件名与 format 匹配（§1.2）
    sha256: string;                       // 外层摘要
    size: number;                         // 外层字节数
    releasedAt: string;
    filesDigest?: string;                 // asset-zip-v2 建议携带（= §1.5 第 5 条的 fileManifestDigest）
  };
}
```

规则：

1. **整份严格校验**（沿用 V1-14）：任一条目非法即整份拒绝并回退缓存，不做"跳过坏条目"。
2. v2 条目 `package.format` 缺失/未知 → 整份拒绝（`GM-5032`）；V1.5 Host 默认源指向 v2 时，
   绝不把缺 `format` 的条目当 HTML 处理（避免把 ZIP 当 HTML 下载）。
3. `package.url` 准入沿用 §5.2 的 host allowlist / 同 host / https / 无凭据 / 重定向 ≤5 规则（`registry.js`，不修改）。
4. `size` 上限按 format 取：`html-v1` ≤20 MiB（沿用 `LIMITS.packageBytes`）；`asset-zip-v2` ≤20 MiB（`LIMITS.zip.zipOuterBytes`，同值但独立常量，便于后续分别调整）。
5. `filesDigest` 可选；若存在，安装时 MUST 与实测 `fileManifestDigest` 相等（不符 → `GM-4278`）。

### 5.3 缓存与源选择

| 项 | v1 | v2 |
|---|---|---|
| 缓存文件 | `registry-cache.json`（schemaVersion 1，沿用） | **`registry-cache-v2.json`（schemaVersion 2，新增）** |
| TTL / 陈旧上限 / 手工刷新节流 | `TIMING.registryTtlMs` / `registryStaleMs` / `registryRefreshThrottleMs`（沿用） | 同左 |
| 缓存校验 | `validateRegistryCache`（沿用） | `validateRegistryCacheV2`：`schemaVersion === 2`、`registryVersion === 2`、`sourceUrl`、`fetchedAt`、`etag?`、`truncated`、`games[]` |
| 源绑定 | `sourceUrl` 必须与当前配置一致 | 同左 + `registryVersion === 2` 校验 |
| 旧缓存复用 | 允许（v1 语义不变） | **禁止**：`registry-cache.json`（schemaVersion 1）MUST NOT 被当作 v2 缓存使用；两者文件名与 schemaVersion 双重区分 |

- 显式 `DSH_GAME_REGISTRY_URL` / `config.registry.url` 仍保持**单源**语义（不静默换用户自定义 URL、不自动回退官方）。
- 默认源迁移到 v2 时 MUST 校验缓存里的 `sourceUrl` 与 `registryVersion`；不匹配 → 视为无缓存（重新抓取或进 seed 状态），
  不得"复用旧缓存冒充新目录"（指南 §4.4）。
- 随包 seed（`registry/games.json` + `registry/packages/`）继续只含 `html-v1`（V1-28/社区契约 §3 不变）；
  V1.5 不把 ZIP 写进随包 seed（保持旧客户端与离线兜底简单）。

### 5.4 不可变性与格式变更

1. 同 `id` + 同 `version` 的**字节**（外层 sha256）不可变；任何变化必须升版本。
2. **格式不得替换**：已发布 `1.0.0` 为 `html-v1` 后，`asset-zip-v2` 的同一游戏必须是 `1.0.1`（或更高）；
   违反 → `GM-4282`（`E_FORMAT_POLICY`），发布工具 MUST 在预演阶段就拒绝。
3. `version` 只能递增（沿用内容仓库 CI 历史约束）；v1/v2 投影各自都不得出现版本回退。
4. 变更格式时，`game.json.version`、目录名、文件名、索引条目版本四处必须一致（§1.7）。

### 5.5 catalog v2：release 引用、投影选择、撤下

内容仓库 `catalog/<id>.json` 的 V1.5 形态（扩展 `docs/community-publishing-contracts.md` §2.4，不推翻）：

```ts
interface CatalogV2 {
  schemaVersion: 2;
  gameId: string;
  owner: { login: string; githubUserId: number };
  game: { /* 展示/兼容字段，沿用 */ };
  releases: Array<{                     // 追加不可改写；每条对应一次已审核发布
    version: string;
    format: 'html-v1' | 'asset-zip-v2';
    tag: string;                        // <id>-v<version>
    package: { url: string; sha256: string; size: number; filesDigest?: string };
    media: { cover: string; screenshots: string[] };
    sourceCommit: string;               // 7–40 hex
    reviewSha256: string;               // 审核记录摘要（沿用 reviews/<id>/<version>.json）
    releasedAt: string;
  }>;
  withdrawnAt?: string | null;          // 撤下时间；存在即视为撤下
  createdAt: string;
  updatedAt: string;
}
```

投影算法（生成器 MUST 按此，且确定性）：

1. `active = releases` 中**未撤下**（`withdrawnAt` 为空）且审核摘要仍有效的 release。
2. **v2 投影**：取 `active` 中 `version` 最大者（任意 format）→ 生成 v2 条目（含 `format`）。
3. **v1 投影**：取 `active` 中 `format === 'html-v1'` 且 `version` 最大者 → 生成 v1 条目（沿用 V1 schema，无 `format` 字段）。
   - 找不到任何 HTML release → 该游戏**不出现在 v1 投影**（不是报错）；v2 投影仍可存在。
4. 游戏被撤下（`withdrawnAt` 非空）→ **两代投影同时移除**；`owners`/`reviews`/已发布资产保留（审计不可改写，沿用 V1-38/39 语义）。
5. `generatedAt` 取所有源记录中最大的固定更新时间（非构建时间）；同输入字节一致（沿用社区契约 §2.4）。
6. `catalog` 与两代 `registry` MUST 在**同一个 PR** 内更新（沿用社区契约 §2.4），不允许"部署等待"造成的两代不一致。

> 为什么 v1 投影要保留"最后一个 HTML release"而不是"当前 release 的降级形态"：旧客户端无法理解 ZIP，
> 把它降级成不存在的 HTML 只会制造 404；保留上一个真实存在的 HTML release 才能让旧用户继续可用（指南 §4.4）。

## 7. 资源 URL 与实例绑定资源凭证

> 本节已由 **S-A1 探针 + Lead 裁决**取代初稿的 `/api/game-market/asset?...` 设计。
> 证据：`docs/verification/v1.5/resources.md`（82/82 必须项通过，exit 0）+ `docs/verification/v1.5/raw/resources/`
> （真实 DSH 0.2.1-rc.2 隔离宿主 + headless Chrome 155；未加 `allow-same-origin`、未碰 `~/.dsh`/App）。

### 7.1 资源服务架构：独立 loopback 资源 origin（**已裁决**）

实测硬约束（`resources.md`；代码位置 `dsh-client-connection/lib/index.js:973` `assertFetchRoute`，`:1044-1049`、`:240/:246` Origin/`sec-fetch-site` 围栏）：

1. `connection.fetch.register` **只接受 `/api/*`** 路径；
2. `/api` 前缀请求先过 Origin / `sec-fetch-site` 围栏：opaque-origin iframe 的 `Origin: null` fetch → **403**；
   `no-cors` 的 `<img src="/api/…">` 因 `sec-fetch-site: cross-site` → **403**。

**裁决（Decision V1.5-02）**：V1.5 资源服务使用**独立 loopback 资源 origin**，不复用 DSH `/api`。

```text
资源 origin（loopback，Host 启动时确定；探针已端到端验证）
GET|HEAD http://127.0.0.1:<resourcePort>/res/<instanceId>/<resourceToken>/<relativePath>
```

- **路径前缀设计**：`/res/<instanceId>/<resourceToken>/` 之后就是包内相对路径，因此包内相对 URL
  （`./scripts/main.js`、`../assets/x.png`，规范化后）**自然解析**，无需 `<base>`、无需改写 HTML 字节（§1.10 第 2 条）。
- MUST：该 origin **只提供实例资源路由**（入口文档 + 清单内资源）；MUST NOT 暴露 `/install`、`/save`、
  更新、问答、健康检查等任何 Host 写接口或诊断接口；MUST 只监听 loopback（不绑定 `0.0.0.0`）。
- MUST：资源 origin 的端口/host 在实例生命周期内稳定；同一实例的所有资源响应共享同一 origin，
  CSP 才能用显式 origin（§7.5）。
- 后续（**不是 V1.5 阻塞项**）：向 DSH 上游提出"`/api` 之外的公开 route seam"，作为未来可替代独立 origin 的方案；
  在该 seam 落地前，独立 origin 是唯一已实证可行的路径。

### 7.2 两条凭证与 reload 状态机（**已裁决**）

| 凭证 | 载体 | 消费次数 | 绑定 | 生命周期 |
|---|---|---|---|---|
| 一次性 launch 凭证 | 首次导航 URL：`/entry?gameId&version&instance&launch=<nonce>`（沿用 V1 一次性语义，参数名沿用/以实现为准） | **1 次**（首 GET 200 即消费） | instance + nonce + gameId + version | `TIMING.entryBindingTtlMs`（10 min）或实例退出 |
| 实例绑定资源凭证 | 资源 origin 路径段：`/res/<instanceId>/<resourceToken>/<path>` | 可重复 GET/HEAD | `instanceId`（内部再校验 gameId + version） | 与实例同寿；`/runtime-renew` 同步续期；`/runtime-release` 立即失效；TTL 到期失效 |

**实测 reload 语义（S-A1）**：

| 场景 | 结果 |
|---|---|
| 首次导航 `?launch=<nonce>` | **200**，凭证被消费 |
| 同一 launch URL 重放 | **410**（`GM-4013`） |
| 去掉 `launch`、用资源凭证 GET 同一入口文档 | **200**（可重复） |
| TTL 到期 / `release` 后 | **403**（`GM-4011`） |
| `renew` 后 | 继续有效（200） |

状态机（Runtime MUST 按此实现）：

```text
[idle] --POST /launch--> [launch-issued] --首次 navigate(?launch=)--> [entry-loaded / launch-consumed]
                                                        |
                                    （reload / 重试 / 同实例再次进入）
                                                        v
                                    [resource-credential-url]  ← 必须用资源凭证 URL，禁止复用 launch URL
```

- MUST NOT：Runtime 在 `launch-consumed` 之后再次导航到 launch URL（会得到 410 与空白帧）。
- MUST：入口文档加载失败/重试/iframe 重建时，用**资源凭证 URL** 重新导航；
  若误用已消费 launch URL，Host 返回 **410 `GM-4013`**，Client MUST 显示真实错误（"启动凭证已使用，正在刷新"）
  并自动改用资源凭证 URL，**不得静默空白**。
- MUST NOT：把资源 token 用在 `/entry`；把 launch nonce 当资源凭证；用 A 实例凭证读 B 实例/游戏/版本的资源。

`/entry` 的服务文件由安装记录 `entry` 字段决定（§6.2）：`html-v1` = `entry.html`（语义不变）；
`asset-zip-v2` = 描述符 `entry` 指向的文件。对 `asset-zip-v2`，entry 文件的 sha256 MUST 等于
`files[]` 中该路径的 sha256（不再与外层 sha256 比较，外层绑定整个 ZIP）。

### 7.3 资源路由与响应契约

| 项 | 规则 |
|---|---|
| 校验顺序 | 资源 origin 前缀匹配 → `instanceId` 存在且未 release → `resourceToken` 与实例匹配且未过期 → 路径命中该实例的**已校验清单**（`files[]`；`html-v1` 只允许 `entry.html`） |
| 路径 | 只接受规范化相对 POSIX 路径（§4.2 规则复用于请求）；MUST NOT 接受绝对路径、`..`、编码穿越（`%2e%2e`/`%2e`）、目录（以 `/` 结尾）、描述符与 `game.json` |
| 映射 | 只映射到 `packages/<id>/<version>/` 下的清单路径；不做目录列举；不做 `index.html` 隐式补全；不在实例间/版本间回退 |
| 方法 | `GET`/`HEAD`；其他方法 **405**；写操作一律 POST（D-028），且资源 origin 上不存在写接口 |
| 响应头 | 精确 `content-type`（按扩展名+魔数，`charset=utf-8` 仅文本类型）、`content-length`、`cache-control: no-store`、`x-content-type-options: nosniff`、`referrer-policy: no-referrer`、`access-control-allow-origin: *`（匿名、无凭据；见 §7.4） |
| 重定向 | MUST NOT 302/307 到公开资源目录或任何其他 origin |
| 日志/遥测 | `<resourceToken>` MUST 在日志、错误 `details`、诊断记录中脱敏（`/res/<instance>/<redacted>/…`）；不得进遥测 |
| 错误 | 缺参/格式错 `GM-4002`；token 无效 `GM-4010`；过期/release `GM-4011`；过期 launch URL 重放 `GM-4013`（410）；跨实例/游戏/版本 `GM-4039`；路径不在清单/文件缺失 `GM-4043` |

### 7.4 资源 origin 的安全边界（CORS / 缓存 / 外发）

已实证（S-A1）并冻结：

1. `Access-Control-Allow-Origin: *` 匿名读取；**无** `Access-Control-Allow-Credentials`、**无** `Set-Cookie`、**无**任何 cookie 参与鉴权。
2. 实例资源 `cache-control: no-store`；`referrer-policy: no-referrer`；`nosniff` + 精确 MIME；
   **不设** restrictive `Cross-Origin-Resource-Policy` / `Cross-Origin-Embedder-Policy`（会破坏 opaque-origin 载入）。
3. 不 302 跳公开目录；不在错误响应里回显磁盘路径。
4. **CSP 是必需的外发边界，但只覆盖「子资源外发」一类**：
   - **子资源外发**（`no-cors` `<img>`、POST/GET 请求、`sendBeacon`、WebSocket 等）：无 CSP 时 CORS **挡不住**
     （第三方 origin 实测收到 `no-cors` `<img>` 与 POST 数据），因此入口文档 CSP MUST 含
     `child-src 'none'; worker-src 'none'; frame-src 'none'; object-src 'none'; base-uri 'none'; form-action 'none'`
     （详见 §7.5），且 `connect-src` 只允许实例资源 origin。
   - **子文档自身的导航**（`window.location.*`、`location.href=…`、`<meta http-equiv="refresh">`）：**不是**子资源外发，
     子文档自己的 `connect-src`/`frame-src 'none'` **拦不住它自己的导航**（CR-P1 实测：游戏 `location.replace(外部地址)`
     时目标服务真的收到请求）。这条边界由**嵌入文档的 `frame-src`** 提供，见 §7.5.1。
5. 资源 origin MUST NOT 承载任何可改变 Host 状态的接口；`/install`、`/save`、更新、问答等只在 DSH 认证的
   `/api` 链路上，且 MUST NOT 因资源 origin 的存在而放开跨域（指南 §4.3）。

### 7.5 CSP（只在入口文档发送，用显式 origin，不用 `'self'`）

实测（S-A1）：sandboxed opaque-origin 文档里 `'self'` 在 Chromium 155 会按入口 URL origin 放行，
但这是实现细节、跨引擎未验证、且资源 origin 与入口 origin 不同时会静默失效。
**裁决（Decision V1.5-03）**：CSP 采用**显式 origin** 形态；`'self'` 语义只作实测记录，**不作为设计依据**。

CSP 只在**入口文档响应**发送（`/entry` 首次导航、以及资源 origin 上入口文档的响应）；资源响应（JS/CSS/图片/音频/字体/JSON）
不再重复发送 CSP（由入口文档的 CSP 约束其加载）。
**wrapper 文档是另一份 CSP**（`frame-src <resourceOrigin>; child-src <resourceOrigin>`，见 §7.5.1）；
本节下面列出的指令描述的是**游戏入口文档**。

`asset-zip-v2` 入口文档 CSP（MUST，逐指令）：

```http
content-security-policy:
  default-src 'none';
  script-src http://127.0.0.1:<resourcePort>;
  style-src http://127.0.0.1:<resourcePort>;
  img-src http://127.0.0.1:<resourcePort> http://127.0.0.1:<resourcePort> data:;
  media-src http://127.0.0.1:<resourcePort>;
  font-src http://127.0.0.1:<resourcePort>;
  connect-src http://127.0.0.1:<resourcePort>;
  frame-src 'none'; child-src 'none'; worker-src 'none'; object-src 'none';
  base-uri 'none'; form-action 'none';
  frame-ancestors <DSH web origin 精确值>;
```

（`img-src` 中重复项为实现示例，落地时去重；`data:` 仅图片，沿用 V1 的 icon/素材 data URI 语义。
**不包含** `upgrade-insecure-requests`：资源 origin 是 loopback **http**，该指令有把子资源请求升级为 https 而失败的风险，
S-A1 实测通过的 CSP 不含它；将来若要使用，必须先单独实测并记录。）

- **`connect-src http://127.0.0.1:<resourcePort>` 是「同 origin 放行、其他 origin/scheme 阻断」的运行时权威边界**（Q-6 裁决）。
  注意 CSP **按 origin 匹配，不是按「绝对 vs 相对」匹配**：指向同一资源 origin 的**绝对 URL 也会被放行**
  （如 `http://127.0.0.1:<resourcePort>/res/…/levels/x.json`），而相对 URL 一旦解析到别的 origin 同样被阻断。
  因此 §4.7 的「拒绝绝对/协议相对 URL」是 **validator 的创作期规则**（保证包可移植、可静态审计、可跨实例一致），
  **不是安全证明**，也不得被描述成"绝对 URL 会被 CSP 拦下"。

`html-v1` 入口文档 CSP：**保持 V1 现状**（`script-src 'unsafe-inline'`、`style-src 'unsafe-inline'` 的单文件形态，不回归），
并 MUST 追加 §7.4 第 4 条的「子资源外发边界」指令（`object-src/base-uri/form-action/frame-src/child-src/worker-src 'none'`）；
`frame-ancestors` 仍按 V1 的可配置 allowlist（沿用 V1 契约 `config.security.frameAncestors`，见 `docs/V1-CONTRACTS.md` TBD-05；
**这是 V1 已冻结的配置键，不是 V1.5 的未决项**）。
`M1 落地前置（归属 M1，A01）`：追加外发边界后四款旧游戏回归必须重跑确认（预期不受影响：它们不使用 frame/worker/base/form）。

**`asset-zip-v2` 禁止内联（裁决 3，从严）**：

| 禁止项 | 判定 | 错误码 |
|---|---|---|
| 内联 `<script>` 块（含 `<script>` 无 `src`） | 解析包内 HTML | `GM-4283`（`E_ASSET_INLINE_FORBIDDEN`） |
| 内联 `<style>` 块、`style="…"` 之外的样式内联 | 同上 | `GM-4283` |
| 内联事件处理器属性（`on*=`，如 `onclick`/`onerror`） | 同上 | `GM-4283` |
| `javascript:` URL | 同上 | `GM-4283` |

- 因此 `asset-zip-v2` 的 CSP **不含** `'unsafe-inline'`；其脚本/样式 MUST 全部外链为清单内文件。
- 拒绝文案（用户可见，本地化 key 前缀 `pkg.inline.forbidden`）：
  "资源包不允许内联脚本、内联样式、内联事件处理器或 javascript: URL；请改为外链文件后重新打包。"
- 理由（裁决记录）：① 严格 CSP 是可自动断言的安全属性，而 `'unsafe-inline'` 会让该断言失效；
  ② v2 的定位就是真多文件包，内联片段可平移到文件；③ 从严后再放宽是加法且可复核，先宽后严会破坏已发布作者包。
- M1 validator 用例（加入 A03 拒绝矩阵）：内联 `<script>`、内联 `<style>`、`on*=` 属性三类**各一条**必须被拒绝，
  且**不得**产出版本目录；另加一条"外链同内容可通过"的正例。
- 逃生口：若真实作者反馈强烈，单独评审"允许内联并加 `'unsafe-inline'`"，**不在 V1.5 默认放行**。

#### 7.5.1 iframe 自导航边界（CR-P1 实测；M1 必读）

**问题**：sandboxed iframe 内的游戏执行 `window.location.replace(外部地址)` 时，**目标服务真的收到请求**；
子文档自己的 CSP（`connect-src`、`frame-src 'none'`）**约束的是它自己的子资源加载，不约束它自己的导航**。

证据：`docs/verification/v1.5/raw/resources/cr-p1-selfnav.json`（探针 `scripts/verification/v1.5/assets/probe-selfnav.mjs`，
exit 0，4/4 as-expected，Chromium 155）。四个用例都带**同源 boot beacon** 作正向对照，证明「没泄漏」不是「游戏没跑起来」：

| 用例 | 嵌入文档 `frame-src` | 游戏运行 | 外部请求 | 结论 |
|---|---|---|---|---|
| C1 host 页面**无 CSP**（现状） | 无 | ran=true | **leaked=true** | **缺口复现**：现状下自导航可外发 |
| C2 host 页面 `frame-src <resourceOrigin>` | 有 | ran=true | leaked=false（Chrome 明确报 `Framing '…' violates … "frame-src http://127.0.0.1:58302". The request has been blocked.`） | 阻断成立 |
| C3 **平台自服务的同源 wrapper**（wrapper 文档自带 `frame-src <resourceOrigin>`）内嵌游戏 | 有（wrapper 自己的 CSP） | ran=true | leaked=false（静默阻断，无浏览器日志） | **首选缓解成立** |
| C4 游戏文档**自己的 CSP**（负对照） | 无 | ran=true | **leaked=true** | 证明子文档自身 CSP 无效 |

**首选缓解（本轮已验证，无需 DSH 改动，MUST 实现）**：

- 资源服务在 `<resourceOrigin>` 上提供一个**平台自服务的同源 wrapper 文档**，其 CSP 设
  `frame-src <resourceOrigin>; child-src <resourceOrigin>`，由它再内嵌真正的游戏 iframe。
- 这样「非预期导航」的阻断**不依赖 host 页面策略**（C3 实测阻断），也不依赖游戏自身 CSP。
- **Runtime MUST 把 iframe 指向 wrapper**（资源 origin 上的平台自服务文档，静态、无凭证、无游戏内容）；
  wrapper 内嵌的游戏文档仍按 §7.2 的 URL 语义加载：首次导航用一次性 launch URL，其后 reload/重试用资源凭证 URL。
  wrapper 自身不计入 launch 消费，也不承载任何能力。

**替代缓解（仅当将来 DSH 允许时）**：由 host 页面自身设置 `frame-src <resourceOrigin>`（C2 实测阻断）。
**产品实现 MUST NOT 假设 host 页面有该策略**——现状（C1）没有，泄漏可复现。

**纵深防御（不能替代上面的阻断）**：受信 Runtime MUST 把「非预期导航」当失败处理——
监听 iframe 的 `load` 事件与 Bridge 心跳；一旦发生非我方发起的导航 / 心跳中断，立即暂停并销毁实例、显示错误、
**不再授予任何能力**（不再续期凭证、不再接受 SDK 调用）。因为请求可能**已经发出**，检测无法挽回，所以阻断 MUST 由 wrapper 提供。

**M1 回归（归属 M1，A06 扩展）**：自导航一组用例——
正例：wrapper 内导航到 `<resourceOrigin>` 成功、游戏继续；
反例：导航到外部 origin 被阻断且**目标端不产生任何请求**（用本地 sink 服务计数，方法同 CR-P1 探针）。

#### 7.5.2 两层沙箱模型（M1 实测修正，推翻「唯一 iframe 一律 sandbox」）

**M1 真实浏览器实测推翻了一条隐含假设**：§7.5.1 要求 Runtime 把 iframe 指向 wrapper，而 V1 的 Runtime 不变量是
「唯一那层 iframe MUST `sandbox="allow-scripts"`」。两者**不能同时成立**：

- wrapper 是游戏文档的**祖先**；外层 iframe 一旦 sandbox，wrapper 文档变成 **opaque origin（`window.origin === "null"`）**；
- Chrome 对 `frame-ancestors` 检查**整条祖先链**，而 opaque origin **匹配不上任何 host-source**——
  即使游戏文档的 `frame-ancestors` 显式列出了 `<resourceOrigin>` 也一样；
- 结果：游戏文档 HTTP 200 但**被拒绝渲染**（`chrome-error://chromewebdata/`），其 CSS/JS 一个都不加载。
- **A/B 对照**（wrapper 字节与 CSP 完全不变，只去掉外层 `sandbox`）：立刻正常加载、无 CSP 违规。
  证据：`docs/verification/v1.5/raw/m1/blocker-wrapper-frame-ancestors-2026-10-20T03-00-23-977Z.json`（Chrome 155）。

**修正后的沙箱分层（MUST）**：

| 层 | 谁创建 | `sandbox` | 运行 origin | 作用 |
|---|---|---|---|---|
| 外层 **wrapper** iframe | **Runtime** | **不加** | `<resourceOrigin>` | 平台受信静态文档：`frame-src/child-src` 只允许 resourceOrigin（阻断自导航）、`script-src` 仅 nonce、`frame-ancestors <DSH web origin>`（只允许被 DSH 页面嵌入） |
| 内层 **游戏** iframe | **wrapper 文档** | `allow-scripts`（**禁止** `allow-same-origin`） | opaque（`null`） | 游戏代码真正的执行边界；文档 CSP 仍为 §7.5 的精确 `frame-ancestors <DSH web origin> <resourceOrigin>` |

安全不变量（替代表述，**语义等价甚至更强**）：

1. **游戏代码永远运行在 opaque origin 的 sandboxed iframe 里**，不能读 DSH 页面、不能读 wrapper DOM、没有 Host 凭据；
2. 外层 wrapper **不是游戏字节**、不承载凭证、不能读取任意内容，且运行在 **resource origin 而非 DSH origin**，
   因此即使被攻破也拿不到 DSH 页面、`/api` 或宿主能力；
3. **`allow-top-navigation` 始终不存在**，游戏无法导航父窗口；非预期导航由 wrapper 的 `frame-src` 阻断（§7.5.1）；
4. Runtime 仍 MUST 只接受 `event.source === 我们创建的 wrapper iframe.contentWindow` 的 Bridge 消息，
   并保留 instance/nonce 双匹配与 pending id 校验；**MUST NOT** 因为多一层而放宽；
5. **`html-v1` 不变**：仍是 Runtime 单层 `sandbox="allow-scripts"` + V1 `/entry`（本修正只适用于 `asset-zip-v2`）。

**为什么不能选另外两条路**：把游戏文档 `frame-ancestors` 放宽成 `*` 会摧毁反嵌入边界（§7.5 / A06）；
给外层 wrapper 加 `allow-same-origin` 会让游戏字节与资源 origin 同源（项目明令禁止，§14.2）。
因此「wrapper 不加 sandbox + 内层游戏加 sandbox」是唯一同时满足三条 MUST 的组合。

**回归要求（A06）**：DOM 层断言两层 iframe 属性（wrapper 无 `sandbox`、游戏有 `sandbox="allow-scripts"` 且无
`allow-same-origin`），并断言**游戏文档真的渲染**（不能只看网络 200——本次实测正是「200 但 chrome-error」）。


### 7.6 `LaunchInfo` 扩展（向后兼容）

```ts
interface LaunchInfo {              // V1 字段全部保留
  // ...instanceId, nonce, entryUrl, preview, runtimeVersion, sdkVersion,
  //    capabilities, limits, viewport, hostEpoch, mode
  resourceOrigin: string;           // 例：`http://127.0.0.1:PORT`（loopback）
  resourceBase: string;             // 例：`http://127.0.0.1:PORT/res/<instanceId>/<resourceToken>`
  resourceTtlMs: number;            // 当前实例剩余有效期
  entryResourceUrl: string;         // 入口文档的资源凭证 URL（reload/重试用；不含 launch）
  package: { format: 'html-v1' | 'asset-zip-v2'; entry: string; filesDigest: string | null };
}
```

- `entryUrl`（V1 字段）语义不变：**一次性** launch URL（绝不能用于 reload）。
- 旧 SDK/Runtime 忽略新字段即可继续工作（`html-v1` 不依赖 `resourceBase`）。
- Runtime MUST 用 `resourceBase` 作为实例前缀注入 iframe；SDK 暴露 `game.runtime.assetUrl(relativePath)`
  → `${resourceBase}/${normalize(relativePath)}`；`relativePath` 必须先按 §4.2 规范化（越界 → `GM-4039`）。
- 续期：`POST /runtime-renew { instanceId }`（沿用 V1-30）MUST 同时续期 entry 绑定与资源凭证，返回新的 `resourceTtlMs`。
- 释放：`POST /runtime-release { gameId, instanceId }`（沿用 V1-30）MUST 使该实例的资源凭证立即失效。

## 9. 插件更新 adapter（`PlatformUpdateAdapter`）

> **`PlatformUpdateAdapter` 是本项目拟新增的 adapter，不是 DSH API，也不是已存在的服务。**
> 它是 Game Market 自己的接口层：对 UI 提供稳定契约，对下映射 DSH 原生 `pluginManager` 能力。
> 用户可见的"更新插件"按钮语义由本契约定义；任何"一键更新"文案在对应路径未被实测前不得出现。

### 9.1 接口契约（本项目自有）

```ts
interface PlatformUpdateAdapter {
  /** 只读能力与版本盘点；无副作用，可在任意时刻调用。 */
  inspect(): Promise<UpdateInspection>;
  /** 接受已验证的发现记录 id；内部构造 DSH target。 */
  beginUpdate(targetId: string): Promise<{ operationId: string }>;
  /** 进度/结果观察；幂等，可重复调用。 */
  observeUpdate(operationId: string): Promise<UpdateObservation>;
}

interface UpdateInspection {
  host: { requestId: string; release: string | null; commit: string | null; hostEpoch: string };
  client: { buildVersion: string; buildCommit: string | null };
  installed: {
    bundleId: 'dsh-game-market';
    spec: string | null;              // profile 中记录的依赖串（可能为 null）
    specShape: 'git-url' | 'registry' | 'path' | 'file' | 'unknown';
    version: string | null;           // 磁盘 package version
    enabled: boolean | null;
    loadedVersion: string | null;     // 当前**运行**版本（≠ 磁盘版本）
  };
  target: { id: string; version: string; commit: string; spec: string; specShape: 'git-url' } | null;
  capability: {
    hmr: 'present' | 'absent' | 'unknown';   // §9.2
    updatePath: 'in-place-hmr' | 'restart-required' | 'unsupported';
    canBeginUpdate: boolean;
    reasonKey: string | null;                // 本地化 key，如 'update.reason.hmrUnknown'
  };
  compatibility: { enginesOk: boolean; peerOk: boolean; minHostVersion: string; reasons: string[] };
}

/**
 * 更新状态机（唯一权威；UI 只允许按此展示）：
 *   inspecting → installing → applied（安装已应用，**尚未核验**）
 *              → activating（等待生效核验）→ updated（Host + Client 双端确认）
 * 非成功分支见 §9.5.1；`applied` 是**中间态**，任何情况下都不得提前显示"已更新成功"。
 */
type UpdateObservation =
  | { operationId: string; state: 'inspecting'; progress: null }
  | { operationId: string; state: 'installing'; stage: 'install'; progress: null }
  | { operationId: string; state: 'applied'; changed: boolean; bundle: string; version: string }          // 中间态
  | { operationId: string; state: 'activating'; installedVersion: string; awaiting: 'restart' | 'reload' | 'health' }
  | { operationId: string; state: 'updated'; version: string; host: string; client: string }              // 唯一成功终态
  | { operationId: string; state: 'pending-restart'; restartReason: 'no-hmr'; installedVersion: string }
  | { operationId: string; state: 'already-at-target'; reason: 'already-installed' | 'same-commit' }
  | { operationId: string; state: 'verification-failed'; reason: 'response-lost' | 'version-mismatch' | 'ambiguous-install'; installedVersion: string | null; runningVersion: string | null }
  | { operationId: string; state: 'stale-runtime'; reason: 'client-old' | 'host-old' | 'dev-row-shadows-package'; runningVersion: string | null }
  | { operationId: string; state: 'too-late'; note: 'install-continues' }
  | { operationId: string; state: 'cancelled'; cancelledBy: 'host' | 'user' }
  | { operationId: string; state: 'failed'; error: { code: string; message: string }; oldVersionStillRunning: boolean };
```

约束：`beginUpdate` MUST 只接受**已验证的发现记录 id**（来自固定官方索引的校验结果），
不接受 iframe、任意 URL/spec、任意文件路径；UI 与 iframe 都不能直接构造 target。

### 9.2 能力判定契约（HMR；Lead + probe-update 已实测）

**判定对象**：`pluginManager` 服务上下文中的 `hmr` 服务是否存在。实测事实（隔离 profile，Lead 时序采样；probe-update 独立复现一致）：

- t=0s：`manager.ownerContext.get('hmr')` 为 `undefined`（`Service.init` 竞态，hmr 行 `fiber.state=1`）——与
   `docs/verification/v1.5/raw/host-capability/hmr-census-plain.json` 的采样一致（`probeScope.hmr:false`、`fiberState:1`）；
- t≈0.5–2s：稳定为存在（`fiber.state=2`，`managerContext.hmrCtor:"Hmr"`；同一 census 文件的后续采样与 `-expose-internals` 版本一致）；
- 带/不带 `--expose-internals` 结果一致；
- 真实 DSH Desktop：Electron 主进程带 `--expose-internals` 且**进程内**运行 profile（监听 GUI 端口的 PID 即该进程），bundles 含 `dsh-base`，用户 patch 未禁用 `hmr` 行 → **默认 DSH（含真实 Desktop）HMR 能力为"开"**。

契约（MUST）：

```ts
async function detectHmrCapability(manager, { timeoutMs = 5000, intervalMs = 250, stableSamples = 2 }): Promise<'present'|'absent'|'unknown'>
```

1. **必须**在 Loader 树稳定后采样：以固定间隔轮询 `hmr` 服务，连续 `stableSamples` 次得到同一结论才视为稳定。
   服务查询路径（两种等价写法，实施时以实际树结构为准）：
   - 同一 Loader 树内：`ctx.get('hmr')`（本插件自身上下文）；
   - 与 `hmr` 行不同树时：`ctx.get('pluginManager').ownerContext.get('hmr')`（Lead 与 probe-update 的实测写法）；
   两者在实测环境中结论一致，但 MUST NOT 只依赖其中一种写法而不做"服务缺失"判定。
2. 超过 `timeoutMs` 仍未稳定 → 返回 `'unknown'`；
3. **禁止**：用 UA、DSH 版本字符串、`--expose-internals` 是否存在、`installBundle` 的返回值反推能力；
   **禁止**在插件 `apply()` 时刻单次读取并缓存（会命中 t=0 竞态，实测为假阴性）；
4. `'unknown'` 的语义是 **fail-closed**：`canBeginUpdate = false`，UI 显示"暂时无法确认当前安装模式"并给原生插件页入口
   （不得因为"大概率是 HMR"就放行，也不得显示按钮后再失败）；
5. 判定结果 MUST 随 `hostEpoch` 缓存并在 profile/树变化（enable/disable/安装完成）后失效重测。

### 9.3 target spec 形态校验（MUST，probe-update 实测依据）

`installBundle` 的 `already-installed` 判定来自 `specPackageName`（`dsh-plugin-manager/lib/index.js` L1373）：
`known !== undefined` 时直接返回该包名，而 `known` 的取值随 spec 形态不同：

| spec 形态 | `known` 取值 | HMR + 已装时的行为 |
|---|---|---|
| registry 形态（裸包名 / `name@version`） | 包名 | **必被拒** → `application:"failed"`, `error.code:"already-installed"` |
| path 形态（本地目录 / `file:`） | 本地目录 manifest 的 `name` | **必被拒**（同上报错） |
| **git / tarball URL 形态** | spec 字符串与 profile `package.json` 中记录的依赖串做**字符串相等**比较；不等则 `known = undefined` | **放行** → pnpm 正常执行 |

因此 `beginUpdate` MUST：

1. **只构造 git HTTPS URL + 完整 40 位 commit 的 spec**（= 指南 §5.1 的发行形态）：
   `https://github.com/<owner>/<repo>.git#<40-hex-commit>`（形式由 `marketInstallTarget`/发布工具产出，实施时以原生解析结果为准）。
2. 拒绝：裸包名、`name@version`、`github:owner/repo` shorthand、`file:`/本地路径、`#main`/浮动 tag/分支名/短 SHA。
   违规 → `GM-4090`（`E_UPDATE_TARGET_INVALID`），UI 文案"更新目标不受支持"。
3. 可选预检（建议实现）：比较"将要构造的 spec 串"与 `inspect().installed.spec`；
   **完全相同**意味着"已经是目标"→ 直接返回 `state:'already-at-target'`，不发起安装（幂等保护，省一次 pnpm）。
4. dev/link 来源（`specShape === 'path' | 'file'`）MUST NOT 被静默替换为正式包：显示
   "开发模式，前往插件管理切换安装来源"，更新按钮禁用（指南 §5.3）。
   实测补充（U2-10）：存在同 id 的 dev row 时 `installBundle` 会**成功**（依赖串与磁盘都变新），
   但 live row 仍是被 checkout 的 dev 版本（`devMode:true`、fiber 不变）——"装上了但没接管"。
   因此 adapter MUST 在 `inspect()` 里识别同 id dev row，把结果映射为 `stale-runtime`（§9.5.1 规则 7），不得报告更新成功。
5. **spec 字符串不可作为"是否已是最新"的判据**：probe-update 实测显示，用完整 https URL 安装成功后，
   profile `package.json` 记录的依赖串会被包管理器归一化为 `github:owner/repo#<commit>` 形态
   （`raw/plugin-update/s-u2-hmr/boot1/observe-before-b.json` 的 `profile.packageJson.dependencies`）。
   因此"构造的 spec 字符串 === 记录的依赖串"这种相等性预检**不可靠**，且重放记录形态会命中 `already-installed`
   （`raw/plugin-update/s-u2-hmr/boot1/install-recorded-a.json`）。
   正确做法：比较**目标版本/commit**（`inspect().installed` 的可判定引用与 target），
   不以原始 spec 字符串相等作为终态判据；`already-installed` 只有在**已确认 installed 版本/commit == target** 时才映射为
   `already-at-target`，否则按 `unknown` 处理（见 §9.5）。

### 9.4 原生映射表（Host/Client → DSH）

| adapter 步骤 | DSH 原生能力 | 备注 |
|---|---|---|
| 发现/校验目标 | 官方插件索引（`parseMarketIndex` / `marketInstallTarget`，格式 1，`source.type = 'git'`） | 索引是可变发现入口，commit 是不可变安装目标；≤256 KiB、5s 超时、HTTPS、静默检查 ≤6h |
| `beginUpdate` | `ctx.remote.pluginManager.installBundle(spec, { enabled: true, requestId, saveExact: true, registry… })` | **MUST 同时检查外层 `ok` 与内层 `application`/`error`/`packageResult`**；不得只看 RPC 成功 |
| 进度 | `pluginManager` 的 `install-state` / `install-log` 事件（日志脱敏） | 只用于进度与诊断，不作为最终判定 |
| 响应丢失/仍在执行 | `waitForInstall(operationId)` | **`null` 不代表成功、取消或没装过**；必须重新读 `install-state` 与实际版本 |
| 取消 | `cancelInstall(operationId)` | 仅宿主返回 `cancelled` 才算取消；`applying` 的 too-late 不得伪报回滚 |
| 待重启 | 返回 `restart-required` + `restartReason` | 只显示"已安装，重启后生效"；**绝不**把磁盘 version 当运行版本 |
| 实际生效确认 | Client/Host 各自的 `buildVersion`/`buildCommit` 上报 + `/health` 实际版本 + 健康检查 | 双端同时匹配目标才进 `updated`。**不得用 `hostEpoch` 判定进程重启**：HMR 在线替换会让被更新插件重新 apply、`hostEpoch` 随之变化（实测），它只代表插件生命周期 |
| 回滚/恢复 | 原生链路安装**预先记录的旧精确 target** | 不走"先删再装"；不自行 kill App；宿主恢复清单 ≠ 已回滚 |

### 9.5 三条路径的实测/契约语义（按 `docs/verification/v1.5/plugin-update.md` 校准）

| 路径 | 触发条件 | 宿主返回（已实测） | adapter 语义 | UI 文案 |
|---|---|---|---|---|
| **A 首选：HMR + git URL + 新 commit** | 真实 Desktop（HMR=开）、目标是精确 commit、构造的 spec 与 profile 记录形态**不同** | 首次安装 `applied`/`changed:true`/`version:"1.1.0"`；**A→B、B→C 两次连续更新均 `applied`**（`raw/plugin-update/s-u2-hmr/boot1/install-b.json`、`install-c.json`），`/health` 无需进程重启即报新版本；重放记录形态 spec（`github:…`）→ `{"changed":false,"application":"failed","error":{"code":"already-installed"}}`（`install-recorded-a.json`） | `applied` → `state:'applied'`（**中间态**）→ `activating` → 双端核对后 `updated`；`already-installed` **且**已确认 installed 版本/commit == target → `already-at-target`（幂等保护，不是失败）；无法确认版本 → `verification-failed`（重读 install-state） | "正在更新到 X…"；**只有 `updated` 之后**才显示"已更新到 X" |
| **B 非 HMR profile** | `detectHmrCapability() === 'absent'`（实测：hmr 行 `disabled:true`、无 fiber） | `{"stage":"enable","application":"restart-required","restartReason":"no-hmr","version":"1.1.0"}`（`raw/plugin-update/s-u1-nohmr/boot1/install-a.json`；boot2 观测到新进程） | `state:'pending-restart'` → 重启后 `activating` → `updated` | "已安装，重启 DSH 后生效"（**不得**称 updated） |
| **C 不支持/未知** | `hmr === 'unknown'`、`specShape` 非法、dev/link 来源、兼容性不符 | 无（adapter 直接拒绝） | `GM-5038`/`GM-4090`/兼容性错误；按钮禁用 + 原生插件页恢复入口 | "当前无法一键更新，请在插件管理中处理" |

#### 9.5.1 状态机（MUST）

```text
inspecting ──▶ installing ──▶ applied ──▶ activating ──▶ updated        （唯一成功终态）
                    │              │            │
                    │              │            ├─▶ verification-failed（响应丢失 / 版本对不上 / ambiguous-install 无法确认）
                    │              │            └─▶ stale-runtime（Client 仍旧版 / Host 仍旧版 / dev row 遮蔽）
                    │              └─▶ pending-restart（非 HMR；等重启）
                    ├─▶ already-at-target（幂等：already-installed / 同 commit）
                    ├─▶ cancelled（宿主返回 cancelled；`too-late` 不是取消）
                    └─▶ failed（管理类失败，含兼容性/权限/包管理器错误）
```

规则（MUST）：

1. **`applied` 只是中间态**：它是"安装已应用"，不等于"用户看到的版本已更新"。UI、日志、发布说明、诊断记录
   都**不得**在核验前显示"已更新成功/已是最新版"。
2. `updated` 只在 **Host 与 Client 双端**版本同时匹配 target 且健康检查通过后进入（U02/U03 验收）。
3. `restart-required` → `pending-restart`：显示"已安装，重启后生效"，**绝不**当作 updated，也**不**把磁盘版本当运行版本。
4. `already-installed`：**幂等保护**，不是失败、不是错误码。只有确认 installed 版本/commit == target 才映射为
   `already-at-target`；否则按 `verification-failed` 处理（继续重读 `install-state` 与实际版本）。
   URL 形态同目标时宿主可能返回 `ambiguous-install` —— **不得无条件吞掉**：必须核对实际版本/commit 后再决定
   （同目标 → `already-at-target`；否则 → `verification-failed` 并继续核验）。
5. **响应丢失**：`waitForInstall()` 返回 `null` **不代表**成功、取消或没装过 → 重新读 `install-state` + 实际版本；
   无法确认 → `verification-failed`（`reason:'response-lost'`），保存游戏并提示刷新/重启，**不得报成功**。
6. **Client 仍旧版**（Host 新、页面未刷新/未重启）→ `stale-runtime`（`reason:'client-old'`）：先保存游戏，提示刷新/重启；
   此期间保持"待生效"，不重复发起安装。
7. **dev row 遮蔽**（实测 U2-10）→ `stale-runtime`（`reason:'dev-row-shadows-package'`），见 §9.3 规则 4。
8. `too-late`：**不是回滚**。`applying` 期取消返回 `too-late` 时安装会继续完成 → adapter MUST 继续观察，
   核验后进入 `updated`；**不得**显示"已取消/已回滚"（实测：`cancel-at-applying.json` + 安装最终 `applied`）。
9. `cancelled` 仅在宿主返回 `cancelled` 时成立；`not-running` 只表示"当前没有可取消的操作"。
10. 失败时重新读原生状态，区分"失败，旧版本仍运行"与"需恢复旧版本"，不得笼统报错（§9.7）。

### 9.6 `removeBundle` + `installBundle` 组合的安全边界

- **禁止**实现"当前组件 await 卸载自己，再 await 安装自己"（指南 §5.3）：被更新 bundle 的 disposal 会先销毁执行者。
- 组合路径**只有在操作持有者独立于被更新 bundle 生命周期时**才允许：宿主侧服务（`pluginManager`）或原生插件页发起；
  并须持有 profile 范围更新锁、完成活跃实例保存协调、预先记录旧精确 target 作为回滚目标。
- **已实测（§13.1 D-S / Q-7 结项）**：probe-update 用一个**独立操作者**验证了这条要求——`ownerEntryId = "include:plugin-manager"`，
  探针 fiber（uid 48）跨越首次安装、两次在线更新、`removeBundle`、重装全程存活，heartbeat 连续。
  因此"操作持有者独立于被更新 bundle"在**独立操作者**形态下成立。
- **仍然禁止**：把这条实测结论套用到"游戏插件自身作为操作者"的场景上。游戏插件先 `removeBundle(thisPlugin)` 再等自己回来，
  其 disposal 会先销毁执行者——该路径**不得**依赖、不得实现（指南 §5.3）。游戏插件只能用 A 路径（由 pluginManager 持有安装）
  或引导原生插件页。

### 9.7 失败与恢复（诚实语义）

1. 失败时重新读原生状态，区分"失败，旧版本仍运行"与"需恢复旧版本"，不得笼统报"更新失败"。
2. 宿主恢复清单/lock ≠ node_modules/旧运行代码/激活状态全部回滚（指南 §5.3）。
3. 诊断记录（宿主范围或持久化，插件消失后仍可从原生插件页查看）MUST NOT 含凭据、问题内容、完整包管理器环境。
4. 网络失败、磁盘失败、兼容性失败、取消、`applying`、`waitForInstall` 返回 `null`、旧 Client + 新 Host 都要有明确状态（U03 验收）。

> **M3 落地记录见 §17**（发现策略、HTTP 形状、身份冻结、adapter/状态机/协调/恢复的实现落点与未验证项）。
> **2026-10-21 P1 审计修复见 §17.6**：关键恢复记录写入门禁（AUD-01）与 Host 权威启动/恢复屏障（AUD-03），
> 不改变本节冻结的 observation/API 形状。

> **方法学限定（引用本节结论时必须一并保留）**：探针用**本地脚本模型**驱动真实 `dsh-agent-loop` → 原生 `ask_user_question`
> 工具 → 原生 waterfall/UI/Session 日志，**不是真实 DeepSeek 模型调用**；"游戏面板"是**同形探针面板**

### 10.1 能力面与判定（de facto，非稳定公开接口）

| 项 | 契约 |
|---|---|
| 首选读取路径 | `ctx.uiSession.sessionStatus` 的 `pendingInteraction`：由原生 `dsh-client-ui-user-questions` 发布的**活 `PendingQuestion` 对象**（`PROJECT_MEMORY` §3.1 的 hook 供 selector 读取） |
| 结算路径（open） | 该对象的 `answer(batch)`；原生 Session 会记录同一 `callId` 的 `tool/call` → `tool/result`（含答案），Turn 继续直到结束 |
| 结算路径（continued） | `ctx.remote.userQuestions.answer(sessionId, callId, batch)`（de facto 命名空间 `remote.userQuestions`） |
| **接口性质** | **de facto，不是稳定公开 API**：实例来自原生插件私有类 `PendingQuestion`（无公开 export、无 wire 类型、无版本字段）；blocking 请求**没有 `callId`**、**不进 `userQuestions` projection** → 第三方无法从投影/日志重建，只能靠「唯一活对象 + 事件顺序」关联 |
| 能力探测 | 启动与宿主 `release` 变化后探测：`pendingInteraction` 存在且对象具备 `answer` / `snapshot` / `hasWaterfall` 方法；结果三态 `available` / `degraded` / `unavailable`，随 Session 切换重测 |
| 版本门 | 已知可用基线 `0.2.1-rc.2`；宿主升级后**必须重跑本探针**（`run-all` 脚本）才能继续宣称可用；不做"版本字符串猜测" |
| `degraded`/`unavailable` | 只显示「回到 DSH 会话处理」入口 + 顶部提示条（不伪造表单、不静默吞掉问题、不假装已支持）；**原地普通问答仍是 M4 发布门槛**（Q01），但只在这条 de facto 适配可用时声称 |
| MUST NOT | import 编译后的私有 `QuestionCards`/内部 React 组件；抓宿主 DOM；再注册一个 waterfall listener 抢请求；把 de facto 路径写进发布说明当成 DSH 稳定能力 |

`待验证`：`uiSession.adapter`、`SessionProvider`、`conversation.composer` 的完整可用范围；上游是否计划公开 seam（见 §13.3 S-3）。
`待验证`：若原生 `dsh-client-ui-user-questions` 插件缺失，agent 范围 waterfall 无 answerer（`NO_PROVIDER`/等到 deadline）——
本项目不得因此注册自己的 answerer 抢占。

### 10.2 `open` 路径（blocking pending question）

1. 结算 MUST 通过**活 `PendingQuestion` 的原生回答 channel**（`pending.answer(batch)`）；原生 UI 与游戏面板共享同一个 pending 对象。
2. 实测前提：游戏面板被 `ctx.layout.selectPanel(...)` 选中、原生 composer 已卸载（探针记录 `composerEditorCount=0`）时结算成功（`{ok:true, elapsedMs:0}`）。
3. MUST NOT：调用只处理 continued 的 `userQuestions.answer` RPC；伪造 `tool/result`；自行 cancel turn；**调用 `pending.dismiss()`**（见 10.2.1）。
4. blocking 无 `callId`：面板以 `sessionId + pending.key` 定位；结算前后用 Session 事件（该 Turn 内唯一 open 的 `ask_user_question` tool call）辅证；
   **不得**把浏览器重连后的 projection 当权威（blocking 不 fold；重连后 key 是新的随机值）。
5. 提交后等待原生状态确认再显示"已提交"；不得因为收到任意 `tool/result` 就清除全部提问等待态。

#### 10.2.1 收起/关闭语义（**与指南 §6.3.4 冲突，已由 Lead 裁决，M4 必读**）

实测：对 blocking（unnamed、无 `callId`）卡片调用原生 `dismiss()` 是 **`reject ASK_CANCELLED`** ——
它**真的取消请求**：Session 记录 `tool/result isError errorCode=ASK_CANCELLED`，之后再答会报
`no channel accepts an answer yet`。原生 `PendingQuestion.dismissal` 只有两种取值：
`callId === undefined → "cancel"`；有 `callId` → `"hide"`。

**契约（MUST）**：

1. 游戏视图内的「收起/关闭面板」**只能收起平台自己绘制的面板 UI 状态（含保留草稿）**，
   **绝对不得调用 `pending.dismiss()`**（也不得调用任何等价的原生取消入口）。
2. 只有 timed/continued（**有 `callId`**，`dismissal:"hide"`）才允许 hide 语义；hide 不结算、不取消。
3. 对 blocking 卡片，「拒绝/取消该请求」在 V1.5 **不提供**入口；用户要取消就回会话处理（原生会话仍可处理）。
4. M4 MUST 有断言/单测覆盖「收起面板不会导致 `ASK_CANCELLED`」（含：收起后问题仍可继续回答；Session 无 `isError ASK_CANCELLED`）。
5. 关闭/收起**不是**拒绝、不是 cancel、不发空回答——但实现手段是"只动自家 UI 状态"，不是原生 dismiss。

### 10.3 `continued` 路径

1. 唯一提交入口：`ctx.remote.userQuestions.answer(sessionId, callId, batch)`（timed 问题带 `wait.callId`）；`batch` 与原生语义一致（每题恰一条 answer）。
2. 实测返回：首窗口 `{ok:true, value:true}`；第二窗口/重复提交 `{ok:true, value:false}`；错误 shape 的批次被 `RemoteError` 拒绝；
   回复会开**新 Turn**（实测 `turnStarts=2`），Session 记录 `user/message source.kind=user-question-reply`（同一 `callId`），projection 转 settled。
3. projection 状态序列为 `open → continued → settled`；UI 以该序列收敛，不靠本地计时器猜测。
4. `REPLY_QUEUED` 表示已排队，**不等于**已结束（`待验证`：本轮未逐帧捕获该错误分支，只有代码保证；实测命中 `value:false` 分支）。
5. 取消、已由其他客户端/原生页面回答、丢弃后重新可答：面板必须重新取状态，不重复 steer。
6. 多窗口/原生页面并存时，最多一个提交成功（实测：第二窗口提交被拒）；其余显示"已处理"。
7. `attachWait` 的 claim/ownership 由宿主与原生 UI 管理：claim 持有时宿主 deadline 被暂停、释放后立即结算；无 claim 时按 deadline 返回 `{pending:true}`。
   游戏面板 MUST NOT 启动第二套超时器抢答。
8. 提交成功后显示"继续游戏"，由用户显式恢复；焦点、监听、计时器在收起/返回市场/关闭窗口时释放。

### 10.4 生命周期与并存（实测）

| 场景 | 实测行为 | 契约要求 |
|---|---|---|
| 浏览器重连 | open 问题**重新投递**（新 key、waterfall 活）并可结算 | 重连后重新取状态、不复用旧 key |
| 切换 Session | A 的问题仍可按 `sessionId` 定位并结算，A 的 Turn 正常结束 | 面板必须按 sessionId 重新绑定，旧问题不得提交到新轮次 |
| 原生问答卡并存 | conversation view 下原生卡渲染时，第三方读取同一 pending 对象并 `answer()` 结算；**第三方结算后原生卡不再发布** | 允许并存；不得抢占/劫持原生渲染 |
| 多窗口 | 宿主只结算一次；第二窗口 `value:false`/RemoteError | 面板显示"已处理"，不重复 steer |
| 分页/跳过 UI | `未验证` | 首版不做分页与跳过（与 DSH 原生语义一致前不发明） |

### 10.5 数据与隐私

- 选项提交使用**原始 label**；"推荐"只是 UI 装饰，不得作为新值提交（Q03）。
- 单选：custom 覆盖 selected；多选：custom 追加 selected；每题恰一条 answer；批量不丢题（实测两题批次逐题精确落盘）。
- 草稿只在该浏览器 Session 生命周期内保存；**不写日志、不进存档、不进游戏 iframe**（游戏永远读不到问题/答案）。
- 中文 IME 组合中 Enter 不提交；按钮可键盘访问；`role="dialog"` 用于真实表单，`status` 只用于信息气泡（不混用）。

### 10.6 危险审批边界（不复制）

`ask_user_question`（选择/输入/计划审阅）与 `approval/request`（危险工具授权）**不是同一协议**。
首版在游戏视图内**只做普通问答**；危险审批只提供"回到 DSH 处理"入口，不复制批准逻辑、不改 policy、不给一次性永久权限
（Q04；无稳定原生 seam 时保持原生入口并在发布说明写明边界）。

### 10.7 本节未验证项（如实保留，不得写成已支持）

真实 DeepSeek 模型调用；真实 Game Market 面板（本轮是同形探针面板）；headed Desktop；
`intent=plan-review` 计划审阅与 `approval/request` 敏感审批路径；原生 Client 插件卸载时的 domain teardown delegation；
分页/跳过 UI；极端同时点击竞态；第一窗口仍 queued 时的 `REPLY_QUEUED` 错误分支（仅代码保证）；
timed 卡片的 hide 语义未在 UI 上逐项走查。

### 15.2 落地期间发现的契约缺口与澄清（按影响排序）

1. **§7.5 入口文档 `frame-ancestors` 必须覆盖整条祖先链（修正）**。
   原文只要求"DSH web origin 精确值"。但 §7.5.1 引入 wrapper 后，游戏文档的祖先链是
   `[resourceOrigin(wrapper), DSH web origin]`，Chromium 要求 source list 覆盖**每一个** ancestor；
   只列 DSH origin 会把 wrapper→游戏 的加载拦掉。
   落地：`asset-zip-v2` 入口文档用 `frame-ancestors <DSH web origin> <resourceOrigin>`；
   `html-v1` 保持 §7.5 原规则（V1 可配置 allowlist，不回归）。
   证据：`packages/host/test/cases/v1.5-resources.js` 的 CSP 逐指令断言；`docs/verification/v1.5/resources.md §5.4` 的 CR-P1 结论。

2. **§7.5.1 wrapper 需要承担 Bridge 点对点 relay（补充）**。
   原文只说 wrapper 负责内嵌游戏。但由于游戏在 wrapper 的子 iframe 内，`window.parent` 是 wrapper，
   若 wrapper 不转发，Runtime 拿不到游戏 window 的引用，只能弱校验 `postMessage` 来源。
   落地：wrapper 只做两条点对点转发（`event.source === parent` 下行、`event.source === gameFrame.contentWindow` 上行），
   不广播、不解析/改写 payload、不持有能力；Runtime 仍只接受 `event.source === 我们创建的 wrapper iframe.contentWindow`，
   并保留 instance/nonce 双匹配与 pending id 校验。wrapper 不消费一次性 launch（只有游戏文档消费）。

3. **§7.6 `LaunchInfo` 需要两个 wrapper URL 字段（补充）**。
   `wrapperUrl`（首次导航，内嵌一次性 launch URL）与 `wrapperResourceUrl`（reload/重试/iframe 重建，
   内嵌 `entryResourceUrl`）。二者均**可选**：`html-v1` 与旧 Host 不提供，Runtime 回退到 V1 直接 `entryUrl`。
   `entryUrl` 语义按 format 分叉：`asset-zip-v2` 是 resource origin 上的一次性入口 URL；
   `html-v1` 仍是 `/api/game-market/entry`（不回归）。路径与查询参数用共享常量
   `RESOURCE_WRAPPER_PATH='/wrapper'`、`RESOURCE_WRAPPER_QUERY='src'`，避免 Host/Runtime 各自猜。

4. **`fileManifestDigest()` 必须注入哈希函数（实现约束）**。
   `packages/shared` 是 browser-pure（契约 §13 规则 2：shared 不得 import Node 内置模块），
   因此签名是 `fileManifestDigest(files, sha256Hex)`，由 Host/CLI/测试传入 `node:crypto` 支持的
   `(text) => hex`。这样既保持 shared 可在浏览器包中使用，也不引入第二份密码学实现。

5. **§7.3 资源路径的规范化必须显式拒绝编码分隔符（澄清）**。
   `%2f`/`%5c` 这类编码分隔符必须在解码**之前**拒绝，否则"先解码再校验"会把它变成一个合法的第二段路径。
   实现：`shared/resources.js#validateAssetRequest`。

6. **§8.1 `GM-4012` = 401（对齐）**。
   实现初期 Host 侧曾落 400，M1 收口时按冻结表统一为 **401**（`packages/host/src/errors.js#statusForGm`）。
   `GM-4010`=401、`GM-4011`=403、`GM-4013`=410、`GM-4039`=403、`GM-4043`=404 均按表。

7. **`shared` 键盘返回形状统一（实现约定）**。
   新增纯 JS 校验器统一返回 `{ok:true, value}` / `{ok:false, code, details?}`（单个 `code` 字符串，
   不是 `errors[]`），跨界时由 `errors.js#INTERNAL_TO_GM` 翻译成 `GM-*`。这与既有 `registry.js`
   的 `{ok, errors[]}` 风格不同，是 M1 新增模块的约定（既有模块未改动）。

8. **`categories`/`capabilities` 等展示字段由 catalog 源记录提供（澄清）**。
   §5.5 的 CatalogV2 只定义了 `game`（展示/兼容字段），投影时由 `releaseToRegistryGame()`
   从 `catalog.game` 取值；`asset-zip-v2` 的 `game.json` 仍需满足既有 `validateManifest`（V1 规则不变）。

9. **两层沙箱模型（M1 真实浏览器实测推翻旧假设，新增 §7.5.2）**。
   §7.5.1 要求 "Runtime MUST 把 iframe 指向 wrapper"，而 V1 Runtime 的不变量是 "唯一 iframe MUST
   `sandbox=\"allow-scripts\"`"。真实 Chrome 实测证明二者不能同时成立：外层 sandbox 会让 wrapper 变
   opaque origin，而 `frame-ancestors` 要检查**整条祖先链**，opaque origin 匹配不上任何 host-source，
   于是游戏文档 "200 但 `chrome-error://chromewebdata/`"，资源全不加载。
   修正：**wrapper iframe 不加 sandbox**（受信平台文档、运行在 resource origin、CSP
   `frame-src/child-src <resourceOrigin>` + nonce script + `frame-ancestors <DSH web origin>`），
   **游戏 iframe 由 wrapper 创建并 `sandbox="allow-scripts"`**（禁止 `allow-same-origin`）；
   `html-v1` 保持单层 sandbox 不回归。安全不变量语义等价（游戏永远 opaque），详见 §7.5.2。
   证据：`docs/verification/v1.5/raw/m1/blocker-wrapper-frame-ancestors-2026-10-20T03-00-23-977Z.json`（含 A/B 对照）。

### 15.4 复核修正轮（CR7，2026-10-20，基于固定 head `77c8d0a`）

复核提出 3 项，均属**实现缺口**（不改冻结设计），已修复并补证据。此处记录它们与契约条款的关系：

1. **CR7-01 · 所有可文档化的包内资源都必须自带策略（§7.5 澄清）**。
   原实现只在 `instance.entry` 上发送 CSP，其他 HTML 作为**同源导航目标**被允许（wrapper 的 `frame-src` 只约束跨 origin 导航），
   而它们作为新文档没有策略 → 可外发。修复：`asset-zip-v2` 对 MIME 为 `text/html` **或** `image/svg+xml` 的资源响应
   发送与入口**完全相同**的 asset CSP（SVG 作为文档加载时也能执行脚本，属同类缺口）；`.js/.css/.json/图片/音频/字体`
   仍不带 CSP（`nosniff` + 精确 MIME 已保证不被当文档执行），避免"全量无脑加头"的过度修复。
   `x-entry-sha256` 仍只给入口；`html-v1` 不变（单文件）。
   证据：`docs/verification/v1.5/raw/m1/CR7-01-same-origin-html-prefix-*.json`（修复前：`second.html` 无 CSP、外部 sink
   实际收到 HTTP 请求 + WebSocket upgrade，8 项 required 失败）与 `CR7-01-same-origin-html-*.json`（修复后 21/21，
   sink 零请求，`second.html` CSP 与入口逐指令一致）。

2. **CR7-02 · 保留的历史版本目录必须可回滚（§6.1/§6.4 澄清）**。
   `placePackageTree` 原先只要目标目录存在就返回 `GM-4094`，使"current + previous"的保留目录**只能占空间、不能回滚**。
   修复：目标目录存在时按**实测内容**判定等价（`asset-zip-v2`：逐文件重算 size+sha256 并比对
   `dsh-package.json` 的 `fileManifestDigest`；`html-v1`：实测现有 `entry.html` 的 sha256+size 与待装字节比较，
   **不依赖可能为 null 的 `record.sha256`**）；一致 → 复用目录（不重命名、不重新解压、不重新封存），
   不一致 → 仍 `GM-4094`；同版本换格式仍 `GM-4282`。记录写失败时**不得**删除被复用的目录。
   注意：`zip.js#verifyPackageDirectory` 因此增加 `verifyContents` 选项（默认 false，§6.5 启动恢复保持轻量）。

3. **CR7-03 · Market UI 本地安装必须支持 ZIP 且不得改字节（§1.8）**。
   原实现只收 `.html`，且上传路径按**文本**读取并以 `text/html` 发送，ZIP 字节被 UTF-8 往返破坏
   （实测 2384 B → 2474 B）。修复：文件选择接受 `.dshgame.zip`（扩展名优先判定格式，MIME 兜底）、复用统一二次确认
   （文件名/大小/格式/覆盖版本），并以 **ArrayBuffer 原始字节 + `Content-Type: application/zip`** 上传，全程零文本编解码；
   `html-v1` 路径不变。证据：客户端单测（2384 B 含高位字节样本，source/uploaded sha256 逐字节相等）+
   真实 Client 点击路径的浏览器证据（见 `docs/verification/v1.5/m1-browser.md`「CR7 复核补充」）。

> 这三项都是"契约说了、实现没做到"，不是契约被推翻；因此 §7.5/§6.1/§1.8 正文不变，只在落地记录里补边界。

### 16.2 落地期间的边界澄清（不改变冻结语义）

1. **内置游戏与安装包共用同一条 LaunchInfo/资源路径（§7.6 澄清）**。

### 17.2 落地澄清与决策（不改变冻结语义）

1. **发现入口不可配置**：`PLATFORM_UPDATE_INDEX_URL` 是常量；Host 代码级 transport seam
   （`http.platformUpdateFetch`/`platformUpdateResolveHost`/`platformUpdateTiming`）只供单元测试与隔离探针注入夹具，
   生产由 `plugin.js` 注入全局 `fetch`。任何配置项都不能替换索引 URL 或构造任意 target。
2. **自有格式 1 校验器是生产路径**（Q1）：不 import 宿主的 `@deepseek-ai/dsh-plugin-market-index`；是否可达只作为证据项，
   不影响策略。校验器按公开格式实现，未引入新依赖。
3. **`discovery.state` 枚举与字段语义**：`never`（从未成功）/`checking`/`ready`/`stale`（上次成功超过 6h 且未再成功）/
   `offline`（最近一次失败是网络/超时；保留上次成功 target）/`invalid`（最近一次失败是格式/绑定/大小/重定向拒绝；同样保留上次成功 target）。
   `lastError={code,message,retryable,at,reason}` 只给诊断；`nextCheckAt` = 下一次允许检查的时间（手动节流生效时即节流到期时间，
   否则为自动静默检查时间）；`canRefresh` 表示手动刷新当前是否允许。`anomaly` 只读附加上报同版本不同 commit。
4. **`GM-5039`（新增）**表示官方更新索引不可用/非法（HTTP 503）；**`GM-4091`** 在 H2 用作「另一个平台插件更新正在进行」
   的 busy 码（错误文案必须与游戏安装区分）。**`GM-5040`** 显式 504（见 §8.3 补充）。
5. **target spec 形态**：`target.spec` 与 adapter 构造的安装 spec 都是 M0 实测通过的
   `https://github.com/heswy/dsh-game-market.git#<40hex>`（不是 pnpm 归一化后的 `git+https://`/`github:` 记录串；
   两者字符串不等正是 `already-installed` 预检不生效、更新可放行的原因，见 §9.3）。
6. **`targetId` 是不透明句柄**：`tgt_` + FNV-1a 64（bundle@version#commit）16 hex；`beginUpdate` 只接受与**当前已验证发现记录**
   完全相等的 id，不能据 id 反推/伪造 target。
7. **Host 运行身份激活冻结**：`buildCommit` 在激活时从 `$DSH_HOME/profiles/<profile>/package.json` 的
   `dsh-game-market` 依赖串解析（`github:`/`git+https`/https git 形态），`loadedVersion` 取运行代码的 package version；
   dev row/path 来源 → `buildCommit:null` 且 `installed.devRowShadow:true`。请求时只允许刷新磁盘侧
   `installed.version/spec`，**不得**用磁盘版本冒充运行版本；`/health` 只追加 `buildCommit`/`loadedVersion`。
8. **release 身份**：`platform-updates/release.json` 的 schema 为
   `{schemaVersion:1, version, clientBuildCommit, repo}`；`repo` 接受发布工具实际写出的
   `https://github.com/heswy/dsh-game-market`（`REPO_URL`，无 `.git`），也接受 `.git` URL、`github.com/owner/name`
   与 `owner/name` 简写，统一归一化为 `owner/name` 后精确比较（外来仓库/凭据/查询串/http 一律拒绝）。
   Host 激活时读取自身包内该文件（version 必须等于运行版本，否则忽略并记录诊断），
   得到期望的 Client 身份 `{buildVersion:release.version, buildCommit:release.clientBuildCommit}`；文件缺失时回退
   `{buildVersion:<running version>, buildCommit:null}`。Client 只上报**自身编入**的身份，不得回填 Host 值。
9. **GET `/platform-update` 不含 `client` 字段**：Client 身份经 `POST /platform-update/client-report` 单独上报；
   Host/Client 双端核验只在 observation 的 `activating→updated` 决策中使用。
10. **观测状态机沿用 §9.1/§9.5.1 唯一权威**；`applied` 只是中间态。`updated` 的 `host`/`client` 字符串形如
    `"<version>+<commit>"`；`failed` 额外携带只读 `reasonKey`（不改变状态语义）。
11. **服务懒解析（H2 澄清）**：`pluginManager`/`hmr` 都不在激活时冻结。`plugin.js` 传入 resolver，adapter 每次调用重新读取；
    缺失时 `capability.canBeginUpdate=false`（`GM-5038`），服务随后出现时下一次 `inspect`/`begin` 即恢复。M0 已实测 `hmr` 在
    t=0 缺失、≈0.5s 出现；`pluginManager` 按同一竞态处理，不依赖单一激活时刻读取。
12. **HMR 能力判定实现细节（§9.2 细化，不降低要求）**：`present` = 连续 2 次真值；`absent` 需要**连续缺失 ≥ `hmrAbsenceSettleMs`（2.5s，
    远大于 M0 实测的 0.5–2s 注册窗口）且期间从未见过真值**；探测抛错/单次闪现/翻转都不判 `absent`，超时一律 `unknown`（fail-closed）。
    结果按 `hostEpoch + profile/tree 签名` 缓存，安装完成/树变化即失效重测。
13. **更新忙碌码**：同一目标在途 → 返回**同一 operationId**（重复点击/多窗口幂等）；不同目标在途 → `GM-4091`，文案明确为
    「Another platform plugin update is in progress」，与游戏包安装的 `GM-4091` 区分；`begin` 入口串行化，避免并发创建两个操作。
14. **协调协议落地**：`coordinate` 请求形状按 m3-decisions §2 + Lead 冻结版本；Host 以**自身活跃实例登记表**为准，
    每个实例必须被某个窗口以 `paused===true && saved===true && saveStale!==true` 确认；未知实例/游戏不匹配 → `GM-4002`；
    任一已确认实例未落盘/存档失败 → 立即中止（`failed` + `GM-4096`，`oldVersionStillRunning:true`），**不调用 `installBundle`**；
    15s 内未全部确认同样中止。`idle:true` 窗口必须不携带实例。
15. **恢复语义**：更新记录在**任何包变更之前**原子写入 `platform-update-operation.json`；HMR dispose 后新激活的 Host 读取记录，
    先用运行身份/磁盘状态核对，再用 `waitForInstall(requestId)`（该服务独立于被更新 bundle 存活）；`waitForInstall()===null`
    时继续轮询实际身份/版本，仍无法确认 → `verification-failed(response-lost)`，**绝不报成功**。插件 dispose 时释放 profile
    更新锁（新激活恢复时重新获取），避免升级自身的 HMR 替换把锁卡死；跨进程并发由锁文件心跳/陈旧接管兜底。
    **恢复的 Client 核验窗口**：普通 in-place 激活用 60s 窗口，但从持久化记录恢复时（尤其真实重启后的 page reload
    由用户/探针驱动）改用 `recoveryClientWaitMs`（默认 30min，且被记录的「30 分钟陈旧规则」封顶）；页面 reload 慢
    不得导致 `verification-failed(response-lost)` 抢先判定。`pending-restart` 恢复在运行身份已匹配时**不依赖**
    `waitForInstall()`（其 `null` 不构成失败）。
16. **`inspect().installed.enabled` 来源**：原生 manager 可用时取 `listBundles()` 的 `enabled`；manager 不可用时按契约允许为
    `null`（fail-closed 能力同时为 false），不猜测。`diskVersion`/`recordSource` 同样来自 `listBundles`，仅作磁盘侧展示，
    运行身份仍只来自激活冻结值。

### 17.4 验证/故障注入操作注记（test-only seams）

给 verification 工作流的操作说明：哪些是**产品可见配置**，哪些是**仅测试/探针可用的代码级 seam**，以及如何在真实宿主里
注入「已持久化的更新记录」以复现恢复路径。所有注入只在隔离 `DSH_HOME`（如 `/tmp/dsh-v15/home-*`）进行，**不得写用户日常 profile/App/生产索引**。

**A. 持久化更新记录（恢复路径的唯一载体）**

- 文件：`$DSH_HOME/storages/dsh-game-market/platform-update-operation.json`（原子 JSON；storage 还会保留
  `platform-update-operation.json.bak`）。storage 读取策略：主文件损坏时会隔离并回退 `.bak`，因此**注入时主文件必须是合法 JSON，
  并覆盖/删除旧 `.bak`**，否则可能读到上一次真实记录。
- schema（`schemaVersion:1`，`parseRecord` 严格校验；任一非法 → 记录被忽略，不会恢复）：

```json
{
  "schemaVersion": 1,
  "operationId": "upd_0123456789abcdef",
  "requestId": "upd_fedcba9876543210",
  "createdAt": "2026-10-20T12:00:00.000Z",
  "updatedAt": "2026-10-20T12:00:05.000Z",
  "status": "installing",
  "target": {
    "id": "tgt_6467c02e1abfbd5b",
    "version": "1.3.0",
    "commit": "<40-hex lowercase>",
    "channel": "stable",
    "publishedAt": "2023-11-14T22:13:20.000Z",
    "spec": "https://github.com/heswy/dsh-game-market.git#<40-hex lowercase>"
  },
  "previous": {
    "spec": "github:heswy/dsh-game-market#<旧 commit>",
    "specShape": "git-url",
    "version": "<旧磁盘版本>",
    "commit": "<旧 commit>",
    "enabled": true,
    "loadedVersion": "<旧运行版本>",
    "loadedCommit": "<旧运行 commit>",
    "dataRoot": "$DSH_HOME/storages/dsh-game-market"
  },
  "coordination": null,
  "cancelled": false,
  "observation": { "operationId": "upd_0123456789abcdef", "state": "installing", "stage": "install", "progress": null },
  "hostEpochStarted": "he_0000000000000000"
}
```

- `status` 允许：`coordinating` / `installing` / `applied` / `activating` / `pending-restart` / `terminal`。
- **触发恢复**：恢复只在**插件激活**时启动（`host.js` 调 `updates.start()`，后台执行、不阻塞激活）。真实宿主中：
  1. 最简单的确定性触发 = 重启宿主进程（`dsh web` 重启；也用于 pending-restart 场景）；
  2. 不想重启进程时，可由独立探针插件调用原生 `pluginManager.setBundleEnabled('dsh-game-market', false→true)` 触发 HMR
     重新 apply（注意：不要从被更新的 bundle 自身调用；M0 的独立探针行形态可复用）；
  3. 恢复是异步的：之后轮询 `GET /platform-update` 的 `operation` 或 `GET /platform-update/observe?operationId=` 观察状态收敛。
- 场景对照（注入后期望）：
  - `status:installing|applied|activating` + 运行身份**已是 target** → `activating`（等 client-report）→ `updated`（需匹配的 client-report + health ok）。
  - 同上但运行身份仍是旧版 → 先 `waitForInstall(requestId)`（仅在**同一宿主进程**内 native manager 仍持有该安装时有结果），
    null 时轮询真实身份/磁盘 `recoveryProbeMs`（默认 5s）；仍无法确认 → `verification-failed(response-lost)`，**不会**报成功。
  - `status:pending-restart` + 运行身份已是 target（真实重启后）→ `activating` → `updated`；运行身份仍旧版 → 保持 `pending-restart`。
  - `status:coordinating` → 恢复为 `failed`（"Update was interrupted before installation; retry"），**无包变更**。
  - `updatedAt` 超过 30 分钟的非终态记录 → 直接 `verification-failed(response-lost)`；注入时请用新鲜时间戳。
- 注入后 DB 之外的副作用为零：恢复不会调用 `installBundle`（只有从 `begin` 正常发起的操作才会），也**不会**因记录存在而假装已安装。

### 17.5 V1 真实探测发现的修复（2026-10-21，非 HMR 真机重启）

V1 隔离宿主真实探测（`docs/verification/v1.5/raw/m3/M3-v1-nonhmr-restart-2026-10-21T00-11-21-752Z.json`：
非 HMR profile，A2=344ce99 → B2=ef8197d，真实 Client UI 更新 + 真实宿主进程重启）暴露一个 Host 侧缺陷：
重启后 Host 实际已运行目标 R_B（`/health` loadedVersion/buildCommit 均匹配、磁盘/依赖匹配），但恢复把
`pending-restart` 操作误判为 `verification-failed(response-lost)`。定位到两个叠加原因：

1. **release 身份校验过严（根因）**：发布工具写出的 `platform-updates/release.json` 的 `repo` 是
   `https://github.com/heswy/dsh-game-market`（`REPO_URL`，无 `.git`），而校验函数只接受部分形态，导致
   `parseReleaseManifest` 拒绝整个 release 身份 → `expectedClient.buildCommit` 退化为 `null`。于是真实页面
   （自身身份 `1.2.2` + `clientBuildCommit=0591b90`）的报告无法匹配期望身份（HMR 链路则表现为
   `stale-runtime(client-old)`）。修复：`normaliseReleaseRepository()` 归一化 URL/`.git`/`github.com/owner/name`/
   `owner/name` 形态后精确比较，外来仓库/凭据/查询串/http 仍拒绝（`packages/shared/src/platform-update.js`）。
2. **恢复窗口过早（放大因素）**：真实重启后的 page reload 由用户/探针驱动，非 HMR 场景没有可依赖的旧页面
   report；恢复进入 `activating` 后 60s 内未收到 client-report 就被判 `response-lost`，而真实探测中页面加载
   晚于该窗口。修复：从持久化记录恢复时改用 `recoveryClientWaitMs`（默认 30min，且被记录 30 分钟陈旧规则
   封顶）；普通 in-place 激活仍用 60s。`pending-restart` 恢复在运行身份已匹配时直接 `activating`，
   **不调用** `waitForInstall()`（`null` 不是失败），匹配报告到达 + `/health` ok 后 `updated`；不重装。
