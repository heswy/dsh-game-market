# V1.5 正式对外首版 · DSH 开发指南

日期：2026-10-19。基线：`v1.2.0@f422e8d04b3b3de3f920a794317c0d28ee1246a2`。
执行者：用户选择的 DSH 开发 Agent；主会话负责架构、契约裁决、review 与验收。
目标版本：`v1.5.0`，这是首次正式向外部用户推广的版本；保留既有 v1.0/v1.1/v1.2 历史，不重写 tag。

本文是待实施任务指南，不是完成报告。可复用开发、Git、证据规则统一引用 `PROJECT_MEMORY.md` §1。不得自动派发开发 Agent；不得修改用户日常 DSH profile、生产索引或发布版本来代替隔离测试。代码实施、跨仓库修改和正式发布各按用户授权执行。

## 1. 三个结果，缺一不能宣布正式对外

1. 支持离线、多文件资源包；现有 HTML 游戏继续可用；新增一款真正使用独立 JS/CSS/图片/关卡文件的内置游戏，不能把资源再次内联后宣称支持资源包。
2. 外部用户从 DSH 安装以后，能发现平台新版本，通过一次“更新插件”操作完成宿主管理的安装；允许 DSH 要求重启，但必须保存进度、显示真实状态、重启后确认实际版本。维护者有可重复执行的发版与目录推广流程。
3. 右下角使用与 DeepSeek 标志一致的鲸鱼形象，配合克制动效与精致气泡。普通 AskQuestion 能在游戏视图内完成回答；危险工具授权继续保持宿主审批边界，不把“回答问题”和“批准执行”混为一谈。

正式发布还必须补完旧版本遗留的真实 App 安装/持久化、完整真实玩法流程与外部作者验证。测试过一次公网 Host 不等于真实 DSH Desktop 全部通过。

### 用户实际看到什么

- 安装：从 DSH 的“插件”入口安装正式 Bundle，不要求 clone 仓库或运行 `dev:enable`。
- 更新：市场设置中的“插件更新”显示当前/目标版本与更新说明；点一次更新，平台先保存游戏，再由 DSH 安装。需要重启则显示“已安装，重启 DSH 后生效”，重启后确认新版本。
- 游戏：HTML 与资源包均正常打开、暂停、存档、继续；用户不需要辨别文件结构。
- 提问：鲸鱼提示“有问题需要回答”；点击后游戏暂停，原地出现问题面板，回答后显式“继续游戏”。

## 2. 开工前阅读与宿主事实

先读 `PROJECT_MEMORY.md`、PRD §8–12、`docs/V1-CONTRACTS.md`、开发者指南、社区投稿/运营/契约、`skills/dsh-game-developer/`、`docs/releases/v1.2.0.md` 及 M4 验证记录。

本方案核对过当前安装的 **DSH Desktop / 宿主包 0.2.1-rc.2**，包括应用内 `app.asar/dsh/node_modules/@deepseek-ai/` 的实际实现；不是只凭通用 Electron/npm 经验设计。详细路径、摘要与官方参考见 [DSH 能力核对记录](./2026-10-19-v1.5-dsh-capabilities.md)。上游 master 会变化，实施时重新记录实际 DSH build/宿主包版本，不把文档 master 当成当前安装实现。

| 已确认事实 | 本版必须遵循的含义 |
|---|---|
| 插件是 Cordis Host + Client 的 Bundle；profile 持有依赖、选择与 patch | 更新交给 DSH `pluginManager`；不自己覆盖运行中的插件文件、不手改 profile YAML |

| 未开 HMR 时覆盖安装可得到 `restart-required`；HMR 下已安装包可报 `already-installed` | 一键更新先证明目标 Desktop 路径；HMR 另设能力门，不先卸载自己再靠自身完成安装 |
| 宿主会用随 App 提供的包管理器、profile 的代理与 registry 计划 | 不要求用户安装全局 pnpm，也不自己拼 shell 执行 `npm update` |
| `pluginMarket` 可读用户配置的 DSH 插件索引，但默认没有索引源 | 不假定用户已启用该服务/添加我们的源；不得静默改其全局市场源 |
| DSH 插件索引格式 1 支持 npm 与固定 commit 的 Git target | 正式发行优先采用固定 Git commit 的已有 Bundle；不用 npm 发布权限也能交付 |

| `uiSession.sessionStatus` 暴露当前 Session 的 pending interaction；官方问答 UI 管理原生卡片 | 优先复用该对象和呈现 seam，不重新订阅并抢占原生问答 waterfall |
| 官方品牌组件使用 `@deepseek-ai/dsh-client-ui-primitives` 的 `FishLogo` | 优先复用宿主正式标志；`dsh-brand` 是名义类型库，不能拿它当 Logo 库 |

## 3. M0：先证明宿主能力，再冻结契约

本阶段必须先交付小型隔离探针与 `docs/verification/v1.5/host-spikes.md`，不先铺大量 UI。下面是实际发布门槛，不能仅写“后续研究”。

| 探针 | 必须证明 | 未证明时如何处理 |
|---|---|---|
| S-U1 非 HMR 更新 | 独立测试 profile 中旧 Bundle → 新精确 Git commit，`installBundle` 是否允许覆盖、返回值、旧 Host 是否继续运行、重启后版本与存档 | 路径不成立就暂停更新主线设计并交主会话裁决；不得把打开插件页/复制命令当一键更新 |
| S-U2 HMR 更新 | 重复安装、卸载/重装及当前 Client/Host 销毁时序；操作是否由独立于被更新插件的宿主服务持有 | 没有安全路径的 HMR profile 显式标为不支持原地一键更新，展示恢复方式；若产品要求支持它，先实现/上游提供原子更新 seam 或独立宿主协调器再放行 |
| S-U3 宿主状态 | `application/restartReason`、`requestId`、安装结果丢失、profile 依赖与实际 loadedVersion 的区别；确认 HMR 能力的可靠来源 | 优先由可信 Host adapter 检查注入服务（如 `ctx.get("hmr")`）并核对当前 profile 管理能力；不凭 UA、版本字符串或“试一下卸载”猜模式；不能证明能力就不展示可执行更新按钮 |
| S-Q1 可信问答视图 | 在绑定 Session 的游戏面板内，读取原生 pending question、提交 blocking/open 回答，并在原生会话里观察同一调用结算 | 优先复用原生 pending 对象/可渲染区域；若没有稳定可用接口，先提出 DSH 适配层/小型上游 seam，不能把 continued RPC 错当 open 提交接口 |
| S-Q2 生命周期 | timed 问题继续、浏览器重连、切 Session、多窗口竞争、原生问答 UI 同时在场、delegation/关闭语义 | 与原生路径不一致时保留“回到会话处理”；普通问答的原地回答仍是正式发布必达项 |
| S-A1 资源加载 | 现有 `sandbox="allow-scripts"` 下加载独立 JS/CSS/图片、ESM、fetch JSON、音频；CORS/CSP 与一次性 entry 凭证的关系 | 不允许加 `allow-same-origin` 或放开整个 Host API 来绕过失败 |
| S-B1 正式标志 | 当前 Client 模块加载器能否解析 `FishLogo`、正式 SVG 的许可/来源、浅深色表现 | 冻结可分发的本地官方轮廓资产作为后备，不依赖远程图片 URL，不换回占位鲸鱼 |

M0 提交 `docs/V1.5-CONTRACTS.md`：包格式、两代索引、安装布局、资源 URL、错误码、插件更新 adapter、Session 问答 face、兼容性矩阵。同步 PRD 新增决策。未通过的宿主探针必须有明确阻塞/产品边界，不在代码里静默降级成另一种产品。

## 4. 资源包方案

### 4.1 决策 A：保留 HTML，新增封闭 ZIP 包

V1.5 同时接收：

- `html-v1`：现有 `<id>-<version>.html`，现有 ≤20 MiB、UTF-8/manifest/自包含检查保持。
- `asset-zip-v2`：`<id>-<version>.dshgame.zip`，只含静态前端资源，无安装脚本、Node 模块或任意可执行 Host 扩展。

选 ZIP 是为了作者本地一份文件、审核绑定原始字节、离线安装与完整回滚。这里是新增归档解析攻击面，不能将“能 unzip”视为完成。M0 比较成熟流式 ZIP 库与自实现成本，提交一项明确的依赖决策：允许经 review 的最小归档依赖，不依赖 DSH 私有 node_modules，也不以零依赖为由自写未经验证的完整解压器。最终库、精确版本、许可证、流式限额与失败行为写入契约后实施。

建议包结构（M0 冻结）：

```text
orbit-courier-1.0.0.dshgame.zip
├── dsh-package.json        # formatVersion: 2，entry，gameManifest，逐文件清单
├── game.json               # 游戏 manifest：id/version/SDK/save 等既有语义
├── index.html
├── scripts/main.js
├── styles/game.css
├── assets/ship.webp
├── assets/pickup.ogg
└── levels/level-01.json
```

`dsh-package.json` 最少包含：

```json
{
  "formatVersion": 2,
  "entry": "index.html",
  "gameManifest": "game.json",
  "files": [
    {"path": "index.html", "size": 1234, "sha256": "<64 lowercase hex>"}
  ]
}
```

示例省略其他文件清单；真实包必须列全。描述符自身不列入 files，防止自引用摘要；外层 ZIP 的 SHA/size 绑定描述符与全部字节。逐文件清单按路径排序，含 game.json。v2 的 game.json 为唯一权威 manifest；不要求继续内嵌一份 HTML manifest，重复或冲突必须拒绝。Manifest 游戏语义尽量复用 v1；包封装版本、SDK 版本、游戏版本不能混用。

建议初始限额：ZIP ≤20 MiB，解压后总量 ≤100 MiB，≤512 个文件，单文件 ≤20 MiB，路径 ≤240 字符、深度 ≤12；单文件/整体压缩比上限 100:1。Stored/Deflate 两类即可；不支持加密 ZIP、多卷、嵌套压缩包、符号链接、硬链接、设备文件、ZIP64。限额在 shared 常量与同一校验器中集中；预检与实际解压都检查，不能信任中央目录宣称值。

### 4.2 路径与归档检查

- 只允许规范化后的相对 POSIX 路径；拒绝绝对路径、盘符、UNC、反斜杠、空段、`.`/`..`、NUL、编码穿越与混用分隔符。
- 同路径重复、大小写折叠冲突、Unicode 规范化冲突、目录/文件同名、越界条目直接拒绝；先检查冲突，再创建文件。
- 校验本地头/中央目录一致、实际 size/CRC/sha、清单缺失/额外文件、manifest id/version、entry 存在；不允许解压器按默认行为覆盖重复条目。
- 包中只准白名单静态类型；拒绝 HTML 中 `<base>`、外部导航/资源地址、非包内 import、service worker、iframe、eval/动态远程脚本。V1.5 不支持 WASM、Worker、外部网络；后续扩展必须单独定义能力。
- 运行时 CSP 与服务器准入是最后防线；静态正则扫描不能作为“无网络/无恶意行为”的证明。
- 只在独立 staging 解压并验证，失败清理 staging；从不直接写 current 目录。禁止调用系统 unzip/shell 执行作者内容。
- 现有 DSH connection 路由使用 buffered requestBody。上传 ZIP 的入口必须在宿主接收层和应用层分别限额；不允许收到后才无限制 buffer 再判断。超限返回明确错误，不能通过换 content-type 绕过限制；压缩包与解压资源的内存/磁盘预算分别计量。

### 4.3 安装、更新与资源服务

沿用现有全局安装锁、幂等 operationId、atomic write、保留 current + previousVersion 和存档分离。每个版本目录只读发布，写入 install marker 前逐文件验完；安装记录增加 format/entry/fileManifestDigest。更新/回滚迁移必须覆盖旧安装记录缺字段场景。

下载外层 ZIP → 核对 SHA/大小 → 有界解压 → 校验描述符/manifest/清单 → staging 原子提升为版本目录 → 原子切换安装记录。断电/崩溃/第二进程并发时，不得出现“记录指向半包”。运行中禁止替换正在用的版本，保存成功后由用户更新；不破坏旧 Session/score/save 配额与 CAS 语义。

不能把 `/entry` 的一次性凭证直接用在每个资源请求。新增**实例绑定资源凭证**：与 gameId、版本、instanceId 绑定；实例续期时同步续期，release/TTL 到期后失效。entry 仍一次性消费；同一有效资源可重复 GET/HEAD。路径只映射到已校验清单，不接受任意磁盘路径、版本覆盖或目录 listing；canonicalize 一次后严格匹配，不跨实例/游戏访问。

资源请求含凭证时：脱敏日志、`Referrer-Policy: no-referrer`，不将凭证暴露给目录/遥测；HTTP 缓存不得让 release 后还能绕过鉴权读取（实例资源使用 no-store）。不通过 302 跳到公开资源目录。

保持 iframe `sandbox="allow-scripts"`，不加 `allow-same-origin`。ESM 与 fetch JSON 在 opaque origin 下需明确的无凭据 CORS：只在实例资源路由允许 GET/HEAD 的匿名读取；不得连带为 `/install`、`/save`、更新/问答操作开放跨域。脚本、样式、图片、音频、字体与 connect-src 仅允许该实例的资源路径前缀及确有用途的 data 类型；禁止宽泛允许整个 localhost 或 Host origin。优先独立资源 origin；若复用 connection 路由，必须证明路径级 CSP/CORS 和 Host 写接口隔离有效。资源响应 `nosniff`、正确 MIME，不直接把任意 SVG 当可信 HTML；字体/音频失败有降级。

S-A1 必须用真实浏览器验证 CORS、模块 import、动态关卡加载，而不是只测试 HTTP 200。未知实例/失效凭证、跨版本、路径穿越、Origin:null 发起 Host 写请求均需拒绝回归。

### 4.4 两代目录必须并存

现有 v1 客户端会严格校验整份 Registry，直接把 ZIP 条目放进旧 URL 会让旧用户整份目录失败。因此：

- 原 `/registry/games.json` 继续生成 Registry v1，只含可用 HTML 版本。
- V1.5 默认读取新 `/registry/v2/games.json`，支持显式 package.format 与 HTML/ZIP 联合结构；同样严格校验整份索引，不能跳过坏条目。
- 内容仓库从同一审核源生成两个投影。源记录必须能保留一个游戏的最后 HTML 兼容版本与当前资源包版本，不能只读“当前 catalog”后猜旧版本。M0 冻结 catalog v2 的 release 引用/投影选择与撤下语义；归属和审核历史继续不可改写。
- 同 id/version 的字节不可变；HTML 转 ZIP 必须升游戏版本，不能借格式更换覆盖原版本。
- 撤下一个游戏同时从两代投影撤下；保留 owners/reviews/已发布资产。旧客户端可继续玩已安装包，不远程强杀。
- 平台仓库测试、内容仓库 toolchain pin/CI、维护者 prepare/validate-assets/审核 SHA 绑定都必须认识两种包；ZIP 外层摘要和内部清单缺一不可。
- 显式 file/HTTPS Registry 配置保持单源；不静默换用户自定义 URL。V1.5 默认源迁移时校验缓存的 sourceUrl 与 schema，不能复用旧缓存冒充新目录。

### 4.5 新内置游戏与开发者体验

新增内置 `orbit-courier`（轨道信使）：短局街机收集/避障，键盘可玩、鼠标可选，单局约 120 秒，具有分数、最高分、暂停与 Continue。独立 JS/CSS、至少一张真实图片、一份关卡 JSON、一个本地音效必须实际加载；音效需首次用户手势解锁并可静音。与现有四款共存，不替换 Snake，不改旧游戏 id 或存档。

它的构建目录与普通资源包使用同一校验器/资源服务，标记 builtin、不可卸载。另做非内置资源包验收 fixture，验证真实安装/更新/回滚；不能用 builtin 免安装路径代替 ZIP 安装证明。完整游戏体验也属于验收，不能只交技术展示页。

CLI `create/build/validate/pack/publish`、Simulator、Vanilla/React 模板及 `dsh-game-developer` Skill 均增加显式格式选项。旧命令默认行为保留；新 CLI 可同时校验 HTML/ZIP。React 资源包不走 singlefile 插件，构建用相对 base；validate 检查最终 ZIP，不只是 dist/index.html；输出确定性包、摘要、size/file count/权限与自测清单。Skill 必须指导 AI 独立做出资源包、修非法包并完成 1.0.0→1.0.1 旧 save 兼容演练。

## 5. 平台持续更新：必须接入 DSH 管理器

### 5.1 决策 B：宿主管安装，我们做可信发现、协调和结果确认

三个更新入口不能混淆：

| 对象 | 发现来源 | 执行者 | 用户动作 |
|---|---|---|---|
| Game Market 插件本身 | 平台仓库发布的 DSH 插件索引 | DSH pluginManager / 原生包管理链路 | 插件更新 |
| 社区游戏 | 内容仓库两代 Registry | Game Market 安装服务 | 游戏详情更新 |
| DSH Desktop 应用 | DSH 自身更新器 | DSH | 宿主应用更新 |

本版不接管 DSH App 自动更新、不覆盖 App 文件。插件更新不能依赖用户打开 Creator 并让 AI 运行命令，也不能只给一个 GitHub tag 链接。

正式插件索引建议 `platform-updates/plugins.json`，采用 **DSH plugin-market-index 格式 1**，通过官方 `parseMarketIndex`/`marketInstallTarget` 生成精确安装参数。首版优先 `source.type=git`、本平台仓库 HTTPS URL、完整 40 位发布 commit；包内已带构建产物，不运行 prepare/postinstall 来现场编译。`private:true` 不妨碍 Git 安装；若未来选择 npm，另行处理包名占用、private、凭据与镜像，不将“npm 已发布”写成既成事实。

索引是可变的发现入口，commit 是不可变安装目标；禁止 `#main`、浮动 tag、shell 参数字符串作为更新目标。已发布同 version 的 commit 不可悄悄替换。正式稳定通道排除 prerelease，测试通道显式 opt-in；遇到同版本不同 commit 显示异常，不自动重装。

已有 `pluginMarket` 且用户已配置本索引时可以复用其结果；否则由 Game Market 的受限只读发现 adapter 获取固定官方索引，不能把该服务可选性变成核心功能不可用。校验器采用公开入口与明确兼容性依赖，不能复制私有实现或假定运行时任意内部模块都可导入。索引请求限定 HTTPS/官方来源、≤256 KiB、5s 总时限、手动刷新节流；启动静默检查最多每 6h，一次失败不阻塞游戏，保留上次成功状态但显示离线。更新目标另校验包名、repo、exact version、engines 与允许的通道；目录数据是数据，不能变成 shell 指令。

### 5.2 真正的一键流程

本节接口名称为**本项目拟新增 adapter**，不是捏造的 DSH API：

- `PlatformUpdateAdapter.inspect()`：当前运行 Host/Client 版本、已安装 bundle/source、目标精确版本/commit、兼容性与能力状态。
- `beginUpdate(targetId)`：只接受已验证发现记录 id，内部构造 DSH target；不接受 iframe 或任意 URL/spec。
- `observeUpdate(operationId)`：进度、失败/待重启/待激活确认、实际生效版本。

实现优先让可信 Client 调用 `ctx.remote.pluginManager` 的原生 Remote RPC，更新由内置 pluginManager 持有，不归卸载中的游戏 Runtime 所有；需要 Host adapter 时复用服务/授权，不另开无鉴权 localhost 更新接口。能力缺失不影响市场和游戏运行，只禁用更新操作并给原生恢复入口。

正常非 HMR Desktop 路径：

1. 用户点“更新到 X”；展示目标、变化摘要与“影响当前 profile 的所有会话，可能需重启”。此操作确认后不要求手动卸载/重装。
2. 获取 profile 范围更新锁；盘点本平台全部活跃游戏实例和其他窗口。让活跃实例暂停并确认存档落盘；有实例无法确认则不进入包变更，显示等待/重试。不能只保存当前 tab。
3. 保存**更新前** profile bundle 的 source、精确可恢复版本/commit、enabled、配置与数据位置。存档留在稳定 storage domain，禁止放在包目录或以插件版本作为新根目录。旧配置迁移用 schemaVersion，不重置用户配置。
4. 调用原生 `installBundle(exactSpec, {enabled, requestId, saveExact: true, ...明确的registry参数})`；方法返回的 Remote Result 需同时检查外层 ok 与内部 application/error/packageResult。不要用当前 `inspect` 对已安装 spec 的 `already-installed` 结果判定“没有更新”。
5. 订阅 `plugin-manager/install-state` / `install-log`，日志脱敏；使用 `waitForInstall` 处理仍在执行但响应丢失的请求。`null` 不代表成功、取消或没有安装过，必须重新核对状态。
6. `restart-required` 只显示“新版本已安装，重启后生效”；绝不能把磁盘 package version 当当前运行版本。使用 DSH 有文档的重启入口；没有可用入口就提示用户重启，不能自行 kill App。
7. Client 与 Host 各自报告 buildVersion/buildCommit/hostEpoch。重启后同时匹配目标且健康检查通过才进入 updated；Host 新、Client 旧时先保存再刷新，不让新旧协议混跑。
8. 未重启时可继续使用旧运行版本，更新提醒改为待重启；不能每次点击反复安装。取消仅在宿主返回 cancelled 时算取消，applying 的 too-late 不能伪报回滚。

稳定诊断/操作记录应由宿主范围持有或持久保存，并能在插件消失时由 DSH 原生插件页恢复查看；不只存在 React state。记录不包含凭据、问题内容、完整 pnpm 环境。

### 5.3 HMR、失败与恢复必须诚实

当前宿主 HMR 下 `installBundle` 对已安装包可拒绝，直接 `removeBundle(thisPlugin)` 又会销毁自己。**禁止实现“当前组件 await 卸载自己，再 await 安装自己”的流程。**

- 非 HMR Desktop 是首版必须实证的一键更新路径。
- HMR 支持若在 M0 证明宿主已有安全操作就复用；否则仅显示明确的不支持状态与原生恢复方式，不谎称该模式一键可用。
- 若首发支持范围要求 HMR，也必须有独立于被更新 Bundle 生命周期的原生更新操作/协调器，含授权、锁和恢复。涉及 DSH 改动先独立提出/审查，不擅自改用户 App 或将其塞进游戏 HTML。
- 安装失败时宿主恢复清单/lock，不代表 node_modules、旧运行代码与已激活状态全部已回滚。重新读取原生状态，显示“失败，旧版本仍运行”或“需恢复旧版本”等实际结论；必要时经 DSH 原生链路安装预先记录的旧精确 target。
- 不用“先删再装”的策略来声称原子更新；不能为了更新授予构建脚本通配权限、绕过 engines/peer 检查或扩大 DSH sandbox。
- `link:` / `file:` / dev-enable 的本地开发载入不得被静默替换为正式包。显示“开发模式，前往插件管理切换安装来源”，将一次性迁移和今后常规更新分开。
- 现有 v1.2.0 没有更新 UI，无法事后凭空给它加按钮；内部测试用户通过 DSH 原生插件安装入口完成一次性迁移。正式外部用户从 v1.5 起走上述持续更新。

### 5.4 维护者每次发版怎么做

提供 `release:prepare` 与 `release:promote` 或等价工具，默认 dry-run；计划参数需引用现有 package/version/build 体系，不写一份长期漂移的版本常量。

1. 准备不可变 release commit，package version、Host/Client build 身份、发行说明、engines/peer 和兼容性矩阵一致；构建已提交或已在发行包中，安装不需脚本。
2. CI 全量验证与打包检查；新 profile 从精确 Git commit 实际安装，检查包中 games/registry/资源/SDK/CLI/Skill 全齐。仅 checkout 能运行不算安装包通过。
3. 发布/推送平台版本 tag（依用户授权），从独立机器/干净 profile 解析 target 并核验真实 manifest/version。任何一环失败不推广 stable。
4. **另一个提交/PR** 把不可变发布 commit 加入 DSH 插件索引并设为稳定默认版本，校验索引后最后合并。不能把“包含自己的 commit SHA”的索引强塞进同一个待哈希的 commit，避免自引用。
5. 测试 profile 用 beta/测试索引演练旧版→新版一键更新、网络失败、待重启与旧存档继续；正式发布前至少走两次不同版本，不能只验证首次安装。
6. 内容仓库 toolchain pin 另开 PR 升到正式发布 commit，生成两代目录/校验资产，CI 后合并。它既不是平台更新通知，也不会给用户更新插件。
7. 支持撤回 stable 推广或显式发布修复版本；不重写 tag，不隐式降级用户已经安装的版本。记录用户恢复到上个精确 target 的操作。

首次对外不依赖用户已打开 DSH“发现”实验插件；提供“插件 → 添加插件”的精确安装 spec、最低 DSH 版本和必要的一次性源配置说明。一键更新的最后验收必须由干净用户 profile 完成。

## 6. DeepSeek 鲸鱼、气泡与游戏内问答

### 6.1 决策 C：品牌形象在可信 Client 层

优先采用宿主 `FishLogo` 的正式轮廓；在当前模块解析支持且版本受约束时作为 Host-provided Client 能力使用。若做本地 SVG 后备，记录原始来源/许可证、保持 DeepSeek 正式轮廓和明暗主题，禁止把官方整个 sidebar 品牌插件带入或改宿主品牌 slot。外部推广页面明确本项目与 DSH 的关系，不暗示获得官方发行背书。

形象按钮建议 48px 视觉、至少 44px 点击区域；使用主题语义色，图形本身不变形。running 仅轻呼吸/浮动，waiting 提示环与一次唤醒，completed 一次轻跃，error 静态可识别状态；不持续转圈/闪烁。reduced-motion 下无循环位移，后台/隐藏不跑动画。用 transform/opacity，避免每帧 React setState。

气泡：12–16px 圆角、细边线、低对比阴影，内容与动作清楚；宽 260–320px，离边至少 16px；短提示最多两行，长问题进入独立问题面板。信息气泡用 status，真正交互问题面板用可访问 dialog；不能给含按钮的复杂表单套 role=status。点击/键盘能展开收起，Esc 不提交、不拒绝，焦点返回鲸鱼。窄窗 375px 改为底部 sheet，不溢出、不挡平台返回/暂停按钮。

既有顶部全宽 112px、右下 96×96 平台安全区保持；展开面板属于短时覆盖，游戏被暂停。新内置游戏的关键 HUD 不藏在右下角。气泡样式不可通过全局选择器覆盖 DSH 原生 UI。

### 6.2 问答实现：先复用 pending interaction，不重新造审批器

游戏里显示的是**平台层浮在 iframe 之上的问题面板**，不把问题/答案发给游戏 SDK；游戏不能读对话、触发安装、提交答案或批准工具。

M0 优先路线：绑定当前游戏的 DSH SessionReference，订阅 `uiSession.sessionStatus` / 对应 Session binding 的 pending interaction；复用原生问答 domain face（snapshot/answer 等）及原生渲染区域。`uiSession.adapter`、SessionProvider、`conversation.composer` 的实际可用范围需按当前宿主验证；不得直接 import 编译后的私有 QuestionCards/内部 React 组件或抓取宿主 DOM。

若原生渲染区域会把整套聊天输入一起挂入游戏，或 pending 类型没有稳定可用的问答 face，先提出最小 DSH seam（例如只公开当前 Session 的问答面板/领域 face）。该名称只是设计建议，不是已存在 API。能力契约未确认前不能写“已支持”；原地普通问答是发布门槛，返回会话仅是失败兜底。

确需自绘问题表单时，adapter 仍绑定原生 pending 对象而非自己从 tool/call 参数猜答案状态：

- `open`：通过原生当前请求的回答 channel 结算；不能调用只处理 continued 的 RPC，不能伪造 tool/result。
- `continued`：通过 DSH 原生 `userQuestions.answer(sessionId, callId, batch)` 让宿主 steer；queued 不等于已结束，处理 `REPLY_QUEUED`、取消、已由其他客户端回答与丢弃后重新可答。
- timed/attachWait 的 ownership/deadline 由原生服务与 UI face 管理；不在游戏里启动第二套超时器抢答，不让用户仅打开气泡就意外改变 Agent 行为。
- 所有操作以当前绑定 Session + callId + question ids 定位；换 Session、重连、原生页面回答后重新取状态，旧问题不可提交到新轮次。无需权限/不存在问题时不展示表单。

### 6.3 用户交互细节

1. 问题到达先显示温和提示，不抢焦点；用户打开面板后平台 pause + 强制 save。保存失败保持暂停，显示重试；不把未完成保存写为已保存。
2. 单选、多选、自由文本、多题分页/进度与跳过语义与 DSH 一致；推荐选项可预选，但绝不自动发送。中文输入法组合中 Enter 不提交；按钮可键盘访问，显示提交中/失败原因。
3. 选项提交使用原始 label，不把“推荐”显示装饰当新值；单选 custom 覆盖 selected，多选 custom 可补充 selected；每题恰一条 answer，批量问题不丢其他题答案。
4. 关闭/收起只保留草稿并收起视图，不拒绝、不 cancel turn、不发空答案；原生会话仍可处理。敏感草稿默认只在该浏览器 Session 生命周期中保存，不写日志或公开存档。
5. 提交后等待原生状态确认，再显示“已提交/Agent 继续工作”；不要收到任何 tool/result 就清除全部提问等待态，保留现有 callId/turn 关联。
6. 提交成功后显示“继续游戏”，由用户显式恢复；不在焦点仍在文本框时把方向键传入游戏。回到会话处理、返回市场、关闭窗口时焦点/监听/计时器正确释放。
7. 原生页面、多窗口与游戏面板同时提交最多一个成功，剩余面板显示已处理，不重复 steer。

### 6.4 普通问答与敏感批准分开

`ask_user_question`（选择、输入、计划审阅）与 `approval/request`（执行危险工具的权限）不是同一协议。首版必须完成普通提问的原地回答；危险工具审批默认提供“回到 DSH 处理”，不复制批准逻辑、不改 policy、不给一次点击永久权限。

如果要在游戏视图内处理危险审批，只能复用完整原生审批视图与一次性 decision 审计链，先验证请求身份、内容、拒绝/取消、过期、多窗口竞争及 `never` 策略。没有稳定原生 seam 则保持原生处理入口，并在首版说明该边界。计划审阅 intent 含长文/diff 时优先原生专用呈现；不能隐藏重要内容后仅放“同意”按钮。

## 9. 实现地图、范围控制与最终交付

| 现有位置 | 预期修改 |
|---|---|
| `packages/shared/` | 格式联合类型/校验、ZIP 限额/错误码、Registry v2、catalog/审核绑定，保持旧导出兼容 |
| `packages/host/src/{install,entry,registry,games,config}.js` | 有界 staging、原子版本、实例资源服务、两代目录/默认源、运行版本报告；更新/问答不走游戏能力 |
| `packages/runtime/` / `packages/sdk/` | 多文件 iframe 地址/相对资源支持、资源凭证寿命、旧协议兼容；不加入审批或包安装 SDK |
| `packages/client/` | 可信更新页、DSH adapter、Session 问题面板、正式 Logo/动效/气泡；能力按可用性降级不使整个插件加载失败 |
| `scripts/cli/` / `templates/` / `skills/` | 双格式 build/pack/validate/dev；独立 AI 能按文档实作 |
| `scripts/registry/` / `templates/registry/` | catalog 双投影、v2 发布/审核/资产验证/历史校验；read-only pinned CI |
| `games/orbit-courier/` | 真多文件内置游戏与逻辑测试、资源授权记录、真机玩法证据 |
| 新发布工具/索引 | 可重复 prepare/promote、DSH 格式校验、稳定目标、原生更新对接；内容 pin 单独 PR |
| PRD/契约/指南/PROJECT_MEMORY | 当前事实与提案分离，支持范围与发布门槛统一，不重复创建第二份记忆 |

不纳入本版：多人联网、账号/付费/排行榜服务、远程资源任意访问、原生代码游戏、绕过 DSH 的自更新、自动批准权限、后台强制升级、云存档同步、改造 DSH App 自动更新器。

交给主会话复核时提供：固定 SHA / PR、宿主版本矩阵、M0 探针结论、三条主线验收矩阵、两代客户端兼容证据、真实 Desktop 安装/升级/问答录像、资源包与恶意包/恢复证据、Skill 独立评估、外部作者公网链路、发布/恢复 dry-run、仍未完成项。源码测试通过不能替代这些体验与宿主验收。

建议首个 PR 仅做 M0 及契约；资源包和更新可在契约冻结后分别实施，品牌/问答围绕同一 Runtime 暂停/Session 绑定合并。每个阶段交付可 review 的成果；任何需要 DSH 新能力的事项先明确仓库与接口，不能在末尾才说“宿主不支持”。
