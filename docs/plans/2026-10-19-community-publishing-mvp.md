## 1. 交付目标与实施边界

一句话目标：**开发者提交游戏，维护者试玩通过后执行一次上架工具，检查并合并目录 PR，用户刷新市场即可发现和安装。**

不要求用户购买或管理服务器。投稿、审核、文件托管、目录和 CI 均使用公开 GitHub 仓库；用户机器上的 Host 从公开 HTTPS 地址获取数据，不持有 GitHub 凭据。

完成本版后：

1. 外部作者通过 GitHub Issue Form 投稿，也可用资料 PR；二者进入同一审核流程。
2. 作者交付单文件 HTML、摘要、源码 commit、封面、截图和自测资料。
3. 自动校验和人工验收分开；没有人工验收记录不能正式上架。
4. 平台官方归档审核通过的原始字节，维护者不用手算 SHA、大小或手改大 JSON。
5. 上架工具生成可审查的目录 PR；**合并该 PR 才改变市场目录**。
6. 新增游戏和更新版本不需要重新发布插件。
7. 保留四款首发游戏的基本可用性、离线能力、已安装游戏及存档。
8. 有明确的更新、下架、失败重试和日常运营手册。
9. 交付可分发的开发者 Skill `dsh-game-developer`；开发者把玩法需求和 Skill 交给 AI，即可由 AI 完成开发、验证、打包及待投稿材料。Skill 是本版必做功能，不是后续文档优化项。

本版不做：开发者网站/账号系统、收费/分成、自动内容审核、任意第三方 Registry 聚合、排行榜服务、多文件/zip 游戏包、远程执行安装脚本、包签名协议、已安装游戏远程强制禁用、自动降级、ID 转让后台。

游戏继续使用现有 manifest v1、Registry v1、单文件 ≤20 MiB、storage/score 能力、现有 Runtime/SDK 桥接。不要为了投稿引入破坏性包协议变更，也不要把本任务扩为原定多资源 V1.5。

## 2. 项目规则和开工方式

复用 `PROJECT_MEMORY.md` §1 的开发、依赖、Git 和验证规则；最终以用户最新协作指令为准：主会话负责方案、协调、review 和验收，用户选择 DSH 实现。本任务不要求自动派发子 Agent。

开工先读：

- `PROJECT_MEMORY.md` §1、当前状态；
- `PRD｜DSH Game Market.md` §4、§8.2、§8.7–8.8、§9.6.1、D-037；
- `docs/V1-CONTRACTS.md` 的包、Registry、安装、SDK 契约；
- `docs/developer-guide.md`、`docs/developer-cli.md`、`docs/V1-GAME-ACCEPTANCE.md`；
- 本文后续各节。

从开工时最新 `origin/main` 建隔离 worktree，放在项目既定的仓库外 worktree 目录。建议主分支 `feat/community-publishing`；阶段 PR 可按职责拆分。先比对本文基线至最新 main 的变化，保留用户变更，不回退后续修复。

任务内允许实现所需的 Host/Client、`packages/shared/`、CLI/脚本、模板、测试和契约文档改动；共享字段、配置、错误码和发布行为先按本方案落入 PRD/契约再实现。核心 Host/Runtime/SDK 不新增第三方生产依赖。复用现有校验器、下载器、安装器，避免并行维护第二份包校验规则。

可本地实现、验证、提交并准备 PR。线上仓库创建、账户权限/凭据设置、生产内容上架、插件正式发布和打 tag 是不同操作：未获得用户对应授权时，准备到可审查状态，不自行执行。没有外部权限仍须完成本地实现和模拟验证，明确列出真实联调阻塞项，不把模拟写成上线完成。

## 3. 当前能力与必须解决的差距

| 已有能力 | 本次必须补齐 |
|---|---|
| CLI create/build/validate/pack/publish；publish 只生成本地材料 | 投稿契约、维护者上架工具和真实 GitHub 托管链路 |
| Host 可选择 file 或 HTTPS Registry | 默认官方线上目录 + 明确的随包兜底规则 |
| 单文件包、SHA/大小/manifest/自包含/兼容性校验 | 已审字节与最终发布资产/索引的全程一致性 |
| 目录缓存、6h TTL、14 天陈旧上限、刷新节流 | 投稿发布后的可发现性、失败状态、刷新入口与端到端验收 |
| 随包三款可安装游戏 + 内置 Snake | 将社区生产目录与随包构建生成物分离 |
| 全出血与安全区规范、Vanilla/React 模板 | 将这些规范加入投稿和人工验收，不宣称静态扫描能证明 UI 合规 |

特别注意：`scripts/build-registry.mjs` 只生成 Jump/2048/Breakout，且重建 `registry/packages/`。**禁止把社区目录直接写入这个生成物后称为完成上架**，下一次插件构建会覆盖它。

当前 `packages/host/src/config.js` 的默认目录为随包 file Registry，只有配置/环境变量能切到远程。仅在 GitHub 合并索引不会让已安装用户自动接入新源。

## 4. 两个仓库的职责

### 4.1 平台仓库：`heswy/dsh-game-market`

承载：Host/Client/Runtime/SDK、包校验器、游戏开发 CLI、开发者 Skill、维护者工具、Registry 仓库初始化模板、协议与教程、平台测试。

随包 `registry/` 继续是首发游戏的离线种子，保持确定性生成；不承载社区投稿生产数据。

### 4.2 内容仓库：建议 `heswy/dsh-game-registry`

这是目标仓库名建议，不得假装它已经存在或由当前会话管理。实施时核对用户最终指定的 owner/name；仓库地址作为配置/工具参数，不能散落硬编码。正式默认 URL 必须对应一个已经建立且通过公网验收的公开仓库。

建议结构（本版新增，尚未存在）：

```text
dsh-game-registry/
├── .github/
│   ├── ISSUE_TEMPLATE/submit-game.yml
│   ├── PULL_REQUEST_TEMPLATE.md
│   ├── CODEOWNERS
│   └── workflows/validate-catalog.yml
├── catalog/<id>.json                 # 每款游戏当前上架版本的源条目
├── owners/<id>.json                  # ID 归属：GitHub 数字 user ID + login
├── reviews/<id>/<version>.json       # 审核记录，绑定精确包/图片摘要
├── registry/games.json               # 从 catalog 生成，客户端唯一正式索引
├── toolchain.lock.json               # 可信平台工具仓库与固定 commit
├── CONTRIBUTING.md
└── OPERATIONS.md
```

- 工具实现放平台仓库；内容仓库 CI 只作薄包装，按固定可信 commit 调用，不复制校验算法。
- 平台仓库提供 `templates/registry/` 或等价初始化目录，包含上述文件与初始化说明。不得把它当成新的游戏 create 模板选项。
- `catalog` 由逐游戏条目生成单份 Registry，按 ID 排序；输出仍遵守现有 ≤500 条、≤2 MiB 等限制。
- 生成函数使用源记录中已固定的时间戳，同样输入字节一致；不在每次构建时随意改时间。
- `registry/games.json` 与源条目放在同一目录 PR 中，CI 检查输出没有过期。不能合入源条目却让生产 JSON 等待一次可能失败的部署。
- 审核/作者记录不混入游戏 manifest，不直接进入客户端 Registry schema。
- 初始线上目录应包含三款可安装首发游戏，使用真正可下载的 HTTPS 包和真实封面；Snake 继续内置。当前随包目录的占位 cover 不可原样用于公开上架。

## 5. 作者投稿契约

首批只接受可审查源码的投稿。源码不进入用户安装流程，保留作者原有许可证；禁止把所有第三方游戏自动改写为平台的 MIT 许可。

Issue Form 必填字段：

1. 投稿类型：新游戏 / 更新；游戏 ID、名称、版本、简介、分类、操作方法。
2. GitHub 作者身份、联系方式、源码仓库与**固定 commit SHA**、构建说明。
3. `<id>-<version>.html` 的公开 HTTPS 下载地址、SHA-256、文件字节数、`.sha256` 地址。
4. 封面与 1–5 张真实截图；封面建议 16:9，PNG/WebP/JPEG；素材符合现有大小/格式限制。
5. 代码和图片/音频/字体素材的来源与许可说明、官方归档分发许可确认。
6. 自测：ready、暂停/恢复、before-save、保存/Continue、键盘、窄窗、主题、全出血/安全区、无外网请求。
7. 更新投稿补充 changelog、旧存档兼容性与破坏性变更说明。

提供等价的机器可读 `submission.json` 示例、字段定义和验证器。资料应包含 schemaVersion；拒绝重复/不合法关键字段；规范化后保留作者原始值供审查。表单用于收资料，维护者将核验后的资料交给工具；本版不强求自动解析所有 Issue 正文，也不需要一个有高权限的 Issue 机器人。

资料 PR 与 Issue 使用同一数据契约，不允许作者直接获得生产发布权限。Issue 关闭、打标签或作者自己的 CI 通过都不等于审核通过或上架。

ID 规则：遵守现有格式；首发 ID 和已登记 ID 不得被抢占；更新作者必须匹配 `owners/<id>.json` 中的稳定 GitHub 数字身份。manifest 的 `author.name` 和 PR 内新填的 login 只是资料，不能当成更新授权。ID 归属变更由维护者另行处理，本版不提供自助转让。

### 5.1 开发者 Skill：`dsh-game-developer`（本版必做）

定位：**把开发包规范变成 AI 能实际执行的游戏开发流程**，覆盖新游戏、接入已有小游戏、修复校验失败和发布更新。产出可安装、可验证、可投稿的内容；不保证绕过维护者验收，也不能只生成一份示例 HTML 就声称接入完成。

用户使用示例：

> 使用 dsh-game-developer，帮我做一款单局约两分钟的太空躲避游戏。希望是温暖的手绘风格，支持键盘、暂停和下次继续。完成后给我可安装的游戏包、源码和投稿资料。

开发者只需要表达玩法、风格和约束。AI 负责选模板、实现和验证；不要求开发者先理解平台源码。Skill 应保持用户选择的玩法与美术方向，不把所有游戏强制做成同一个模板的换皮。

**仓库与分发：**

```text
skills/dsh-game-developer/
├── SKILL.md                     # 标准 name/description frontmatter + 执行入口
├── references/                  # 按需读取的包/SDK/呈现/投稿约束
└── scripts/                     # 仅在复用确定性操作确有价值时添加
```

- `SKILL.md` 的 name 固定为 `dsh-game-developer`，描述清楚用于 DSH Game Market 游戏开发、适配、验证和准备投稿，不处理市场平台本身的开发或维护者上架操作。
- 入口简洁，详细规则渐进加载；目录结构按实际需要创建，禁止堆空文件和未完成脚手架。可提供宿主专用 metadata，但核心流程不能依赖某一种 AI 客户端或另一个未分发的私有 Skill。
- 包格式和 SDK 规范仍以现有 shared validator、SDK 类型、开发者指南为权威。Skill 中的详细参考从这些来源整理/生成，给出来源与兼容版本；避免出现与 validator 并行维护的第二套规则。CI 检查关键约束及版本同步。
- 随开发工具一起提供可下载、版本化的 Skill 目录/归档。目录可作为通用 AI 指导直接读取，也要给出至少一个实际验证过的 Skill 安装/调用方式，放在开发者入门文档中。
- 工具版本可追溯到平台 release/commit，包含支持的 manifest、SDK/Runtime 范围；不能写死当前维护者机器的绝对路径，也不能要求外部 AI 访问本人的 `~/.codex/skills`。
- 外部开发者只下载开发工具/Skill 后，能找到 CLI、SDK 类型和模板：给出实际存在的获取方式、校验方式和路径解析。不要写尚未发布的 `npx` 包；允许固定版本平台 checkout/开发工具包作为首版方式。
- Skill 分发归档只是开发工具材料，不能改变运行时游戏仍为单文件 HTML 的规则。不得把开发者机器上的 Skill、提示词、测试密钥或构建依赖打进游戏包。

**Skill 必须指导 AI 实际执行的流程：**

1. **理解需求与选型**：提取玩法、操作、时长、美术与语言需求。信息不足但不阻碍实现时使用合理默认；只有影响玩法或交付的缺项才询问。Vanilla 为轻量默认，已有 React 工程或用户明确要求 React 时使用对应模板。
2. **定位可信工具链**：确认工具版本、模板和 SDK 获取路径；在独立游戏工程中开发。不得修改用户平台安装目录、个人 DSH profile 或平台核心来让游戏通过。
3. **实现真实玩法**：具备开始、游玩、结束/重开及适用的进度恢复；输入反馈和视觉层级完整，不是静态封面或只有成功弹窗的演示。按需求设计有辨识度的视觉，避免把占位文字/字母当作正式封面或截图。
4. **遵守包规范**：单文件自包含 HTML、恰好一份合法 manifest、合法 ID/版本/能力、资源内联、UTF-8 无 BOM、体积上限、无运行时外部网络。React 在开发期可使用模板构建依赖，最终包不能含外部依赖请求或 Vite preload fetch 补丁。
5. **接入 SDK**：ready 成功后启动；按需声明 storage/score 并提供其条件字段；处理暂停、恢复、hidden/before-save、存档/Continue、Session 和适用的分数提交。注册事件/读取只读字段使用真实 SDK API；不得虚构 viewport 订阅接口、静默吞掉关键失败或用浏览器本地存储代替平台存档。
6. **呈现适配**：背景全出血、实际 CSS 尺寸与 DPR、resize、明暗主题和减少动画偏好；关键 HUD/按钮避让顶部全宽 112px 和右下 96×96，明确展开气泡的临时覆盖。允许游戏保持自己的艺术风格，不能把“合规”误解为加一圈空白舞台边框。
7. **先验证再交付**：实际执行 build、validate、pack，读取退出码和输出；校验失败后定位并修正，重跑受影响检查。检查最终包 SHA/字节数、重建一致性、无多余外联。用隔离模拟器/真实 Runtime 验证启动、内部玩法推进、暂停/恢复、读档、窄窗和关键 UI 遮挡；不能拿外壳 playing 代替游戏真的在运行。
8. **整理待投稿材料**：生成源码、可安装 HTML、`.sha256`、submission 数据、真实封面/截图和测试报告；缺作者身份、源码远端地址、许可确认或下载地址时明确列待补项，不编造身份、授权、URL 或截图。已有离线 publish 可生成候选条目；不能把它表述为内容已上传/上架。

遇到缺运行环境、网络或权限：继续完成独立可做的开发与静态验证，交付准确的已验证/未验证清单及复现步骤；不得造成功能已通过的结论。没有用户明确授权，不替作者上传、开投稿 Issue/PR、创建 Release 或执行维护者上架工具。Skill 本身不带发布凭据，也不因加载 Skill 获得外部操作授权。

**最终交付约定：**

- 游戏源码工程与构建说明，工具链版本可追溯。
- `dist/<id>-<version>.html` 和匹配的 `.sha256`；不得只有未打包的 index.html 或源码目录。
- 与本版投稿契约一致的 submission 数据、真实素材及许可来源说明；缺项标为待补，不假装可正式上架。
- 验证报告写实际命令、退出码、包摘要、行为结果、截图与环境边界；区分“静态包检查通过”“隔离 Runtime 通过”“尚待人工审核”。
- 更新任务还需递增版本、changelog、旧存档兼容检查；同版本不得替换包字节。

**Skill 验证不是只检查 Markdown：**

- 检查 frontmatter、命名、相对引用和脚本可执行性；没有死链、维护者路径或脚手架占位符。
- 从仓库外的全新目录读取分发后的 Skill，实际让 AI 完成至少一次从玩法描述到打包的独立任务；评估者不给它额外口头解释或现成答案。
- Vanilla 与 React 均有真实生成/构建/校验/打包证据，React 含类型检查；至少一次真实浏览器行为验证。
- 提供一个非自包含/非法 manifest 的输入，验证 AI 会修正问题后重验，不是篡改 validator、关闭规则或只改报告成绿色。
- 对 1.0.0 → 1.0.1 更新任务验证版本递增和旧存档恢复。
- 评估任务应在隔离目录/测试 profile 内执行，不创建未获授权的公开投稿或正式 Release。AI 自测通过只是待审交付，不是维护者批准。

## 6. 自动检查与人工审核

### 6.1 自动检查：处理数据，不执行作者工程

使用平台可信代码校验：HTML、manifest、自包含、兼容性、包名、大小、SHA、版本递增、ID 归属、条目一致性、图片真实格式/大小、URL 准入和整份 Registry。

- 下载作者产物到独立临时目录，执行现有包校验器；不用作者提交的校验脚本作为结论。
- 不在有发布权限的任务中执行作者源码、npm install、构建脚本、HTML 或 PR 中的 workflow。
- 构建复现或浏览器试玩若执行不可信内容，使用无 secrets、无个人 profile 的隔离环境。
- 下载沿用 HTTPS、精确 host、DNS/地址限制、重定向与大小/超时约束；不为了上架工具绕过 Host 的安全准入。
- 来自 Issue/PR 的文本一律当数据，不拼接成 shell。外部程序用参数数组调用；凭据不落盘或写日志。
- 外部 PR 的检查使用只读 token、不暴露 secrets；不要用带写权限的 `pull_request_target` checkout 并运行投稿代码。
- 工具链锁定到可信平台 commit。投稿 PR 改 workflow、CODEOWNERS、工具锁定或审核策略时，必须作为单独维护者改动处理，不能借一次游戏上架自动接受。

### 6.2 人工审核：绑定被批准的内容

至少检查：

- 玩法和介绍相符，素材许可资料完整，试玩没有明显异常。
- 生命周期与存档/Continue 正常，更新可读取旧存档。
- 键盘、窄窗、明暗主题可用；游戏背景铺满，关键 UI 避开顶部全宽 112px 与右下 96×96，展开气泡不会挡住唯一必要入口。
- 5 分钟真实游戏内推进/暂停/恢复；不能只看 Runtime 外壳状态。

审核记录必须绑定：游戏 ID/版本、来源 Issue/PR、源码 commit、作者数字身份、**批准的包 SHA 与字节数、批准的每张素材 SHA**、审核人、审核时间、验收证据。审核后作者替换 URL 内容，必须阻止发布，不得默默更新摘要。

审核记录由维护者确认并控制。作者在 submission/PR 中自填的 reviewer、approved 或布尔勾选不能授予批准权限；工具必须显示当前执行者、批准人及来源，正式 PR 仍由维护者确认。版本和内容若在最后确认后变化，需要重新审查。

状态：待资料 → 待自动校验 → 待人工验收 → 已批准待上架 → 目录 PR 待合并 → 已上架；另有需修改/拒绝/已撤下。状态标签只帮助管理，生产事实以主分支目录和发布记录为准。

## 7. 维护者上架工具：本版核心交付

新增独立工具入口，避免改变现有离线 `dsh-game publish` 的含义。建议：

```bash
# 以下是需要实现的接口，不是当前已存在的命令。
node scripts/registry/prepare.mjs \
  --submission /path/submission.json \
  --review /path/approved-review.json \
  --registry-dir /path/dsh-game-registry

# 默认只预演。明确执行才允许上传/发布/创建目录 PR。
node scripts/registry/prepare.mjs \
  --submission /path/submission.json \
  --review /path/approved-review.json \
  --registry-dir /path/dsh-game-registry \
  --execute
```

维护者前置条件：本地 Node、Git、GitHub CLI，已登录且对内容仓库有必要权限；检查失败给出可操作提示。不得输出 token。只上传和创建 PR，不自动合并 PR。

### 7.1 默认预演

验证资料、归属、版本、人工批准记录及本地目录状态；下载并核对资产；输出将创建的 Release/tag、资产名、摘要、目录改动和 PR 摘要。预演不写远端，不改生产分支，可以生成本地审查材料。

### 7.2 明确执行

1. 重新校验批准记录，固定本次事务的所有摘要和基线目录 commit。
2. 下载并验证所有资产后，保存到只属于本次事务的临时目录。后续上传只使用这些已验证字节，不在上传时重新取一个未经核对的 URL。
3. 在官方内容仓库创建 draft Release，tag 采用 `<id>-v<version>`，避免不同游戏都叫 v1.0.0。
4. 资产名：包必须 `<id>-<version>.html`，附 `.sha256`；图片使用版本化名称，全部避免覆盖旧版本。
5. 上传完整资产，确认摘要/大小一致，发布正式 Release；仓库建议启用不可变 Releases。若需发布后检查公开地址，失败不生成上架 PR，产物保持未入目录状态。
6. 用**官方最终地址**生成 catalog 条目、ID 归属/审核记录及完整 `registry/games.json`，在内容仓库的新分支提交。
7. 创建上架 PR，正文列出游戏、作者、版本、差异、证据、包/素材摘要、旧存档影响和最终链接。
8. 输出 PR 地址，等待维护者合并；工具到此结束。

目录 PR 合并之前，Release 资产虽可能公开，但不应出现在市场。允许留下未入目录的归档版本，不自动清理可能不可变的资产。

### 7.3 幂等、并发和失败处理

- 用仓库 + ID + 版本 + 批准 SHA 标识事务。
- 同版本同摘要可检查并继续未完成阶段，复用同一 Release/PR；不得重复创建多个目录 PR。
- 同版本不同摘要必须失败，要求作者升版本，不提供覆盖/clobber/强推捷径。
- 某张图上传失败、公开下载失败、生成索引失败、创建 PR 失败，均保持生产目录不变，并提示如何重试。
- 内容仓库 main 移动时重新核对归属/版本和整份索引，生成基于最新 main 的 PR；不覆盖其他游戏的上架改动。
- CI 检查同一 ID 的并发更新，只允许递增版本；合并时使用最新基线检查，避免后合入的 PR 把更高版本覆盖回去。
- 生成过程中不改用户已有未提交文件；工作目录不干净时说明处理方式，禁止 reset/clean。

## 8. GitHub 内容仓库配置

交付可复制的初始化模板和步骤：

- 公开仓库、投稿 Issue Form、PR 模板、CODEOWNERS。
- main 通过 PR 更新，维护者检查并确认、目录校验通过；按仓库可用设置启用分支保护或 ruleset。单维护者可能同时是工具生成 PR 的作者，不能设置成只有本人能审批、却要求一次独立 approval 的死锁流程：单维护者采用 PR + 必须通过的 CI + 人工点击合并；存在第二位维护者时再启用独立审批/CODEOWNERS review。若账户/仓库设置不支持某项，记录真实限制，不伪称已启用。
- 更新 PR 后重新校验，旧审核不应覆盖新包/新素材。
- CI 校验 catalog、owners/reviews、生成输出、正式资产摘要和格式，禁止相对包 URL 出现在远程索引；整份索引无效则阻止合并。
- CI 使用固定可信工具链；第三方 Action 固定完整 commit SHA，最小权限。
- 首版发布工具在维护者本机使用 gh 执行，不要求配置有写权限的投稿机器人；CI 只读即可完成验证。
- 启用不可变 Release 的流程：先 draft、上传齐全、再正式发布；不能依赖发布后再补资产。

GitHub Assets 的实际重定向必须通过真实 Host 下载器测试。若 GitHub 当前使用的正式资产域名不在默认准入列表，只能在实测、核对用途后追加精确 host 并补拒绝测试，不能泛化允许所有 githubusercontent 子域或关闭地址限制。

## 9. Host 目录分发与离线兜底

### 9.1 默认官方源

新版本默认获取官方内容仓库的公开 `registry/games.json`。URL 在一个集中定义处维护；上线前确认公开可达、schema 合法、包与预览均能下载。

优先级：**已有显式环境变量/配置 > 默认官方 HTTPS 源**。保留现有显式 file/HTTPS 配置和开发环境语义，不能把用户自定义目录悄悄混入官方内容或改写用户 profile。

旧版本用户不会因目录 PR 自动接入新源；手册说明首次需要升级插件，或按已有机制手动配置远程源。接入之后，内容更新无需再次升级插件。

### 9.2 默认官方源的选择规则

| 状态 | 展示和安装行为 |
|---|---|
| 有 fresh 官方缓存 | 立即展示，遵守现有 6h TTL |
| 有 stale 官方缓存（未超过 14 天） | 展示缓存，后台刷新；刷新失败仍可使用并标明离线 |
| 冷启动无缓存或缓存过期，网络可用 | 先保证随包游戏可见，后台拉取；成功后切换到完整官方快照 |
| 冷启动无缓存或过期，网络不可用/索引非法 | 使用随包 file 种子，显示简短状态；不让 Market 白屏或卡住 |
| 用户显式自定义源 | 保持自定义源的现有缓存/失败语义，不偷偷回到官方源 |

关键约束：

1. 远程**有效快照是完整权威目录**，不与随包条目逐项合并；否则远程撤下的游戏可能被种子重新补回。
2. 随包种子只在上述兜底状态使用，包含首发可安装游戏，不把社区缓存永久包装为随包资产。
3. 线上缓存和种子保留各自来源；不能将 file 种子写成 remote cache、伪造 fetchedAt 或重置 14 天陈旧限制。
4. 处于随包模式时，安装必须走对应 file 包路径；处于线上模式时走官方 HTTPS 包和 SHA 校验。不能展示种子却用远程来源解释相对 URL。
5. 内置 Snake 和已安装游戏仍按既有目录合并逻辑可用；远程缺少条目不能删安装包、存档或导致已安装游戏无法在我的游戏中启动。
6. 默认源初次拉取不能阻塞首屏的基本游戏目录。沿用超时/单飞刷新/后台刷新纪律。
7. Host 拉取与缓存，Client 只调用同源 API，不让 Client 直接访问 GitHub。

缓存/source 状态的实现可以在现有 Registry 服务上加组合层，不得直接把所有来源数据塞进同一个 cache.games。先写选择状态机和测试，再接 UI。若暴露新字段，给契约和兼容性说明；内部字段无需进入公共协议。

### 9.3 市场交互

提供明确、可用的“刷新游戏目录”操作；已有入口够清楚则复用。刷新后新游戏立即出现在成功返回的结果中；保留合理的现有 5 分钟节流和 429 提示，不每点一次都 force 绕过。

离线/刷新失败时用简短提示说明“正在显示缓存”或“暂时显示随包游戏”，保留重试。不要恢复此前删掉的常驻“更新于 xx seconds ago”页脚，也不要把 JSON、Registry、SHA 等实现词塞进普通用户主流程。

游戏新增、更新、撤下后，用户已有搜索/分类、列表焦点和安装态保持一致；UI loading/error/empty 状态要覆盖。

## 10. 更新、撤下与运营记录

- 更新沿用投稿/审核/归档/目录 PR 流程，版本严格递增；已存在版本不可替换字节。
- 同一 ID 的第一次上架时间保留，更新修改 updatedAt/changelog；其他人工运营标记按审查结果保留，不能因更新自动丢失。
- 检查旧存档兼容；不兼容时明确提示并要求修复或单独评估，不自动清空用户数据。
- 撤下通过目录 PR 删除正式 catalog 条目并重新生成索引，保留 owners、历史 review 和已发布资产供审计。
- 撤下影响后续发现和安装，不自动卸载/禁用已安装游戏。本版不承诺紧急远程封禁。
- 回退目录 commit 只影响目录，不等于已安装版本降级。正常修复使用更高版本包；必要时按现有人工恢复机制处理。
- 离线陈旧缓存/随包兜底可能暂时保留旧目录可见性，手册明确它不是实时撤销系统。需要强制撤销时另做独立设计。

## 11. 实施阶段与建议 PR 拆分

| 阶段 | 主要交付 | 阶段验收 |
|---|---|---|
| M0 契约 | 更新 PRD/契约；submission、review、owner 字段；源选择状态机；工具接口；目录模板与 Skill 的版本/分发结构 | 与现有 schema/缓存/配置兼容，迁移规则明确 |
| M1 投稿与目录 | 内容仓库初始化模板、表单、逐条目录生成器、只读 CI、投稿/运营教程、`dsh-game-developer` Skill | 本地样例能生成合法 HTTPS Registry；Skill 可在仓库外独立指导 AI 开发、验证与打包 |
| M2 上架工具 | dry-run、gh 检查、批准摘要绑定、Release 归档、PR 创建、重试/并发防护 | 模拟 GitHub API 故障矩阵通过，预演零远端写入 |
| M3 市场接入 | 默认线上源、随包兜底、缓存/source 隔离、刷新/失败 UI、旧配置兼容 | 真实 Host 安装/更新/离线链路通过，首发游戏不回归 |
| M4 真实联调 | 用户授权的 GitHub 目标仓库配置、真正公网包与预览、一次由 Skill 指导 AI 制作的新投稿/更新/撤下 | 以非项目作者视角完整跑通，归档 Skill 行为与上架证据，交 Codex 复核 |

可以先并行准备本地模板/工具，但不要在 source 状态机未明确时修改 Host 的全局缓存行为。不要为了让 M4 看起来完成而用本地 TLS 服务替代公网 GitHub 验收。

| C-12 | 配置兼容 | 显式 HTTPS/file/环境变量优先，原有配置不改写、不混源 |

| C-16 | 权限边界 | fork/Issue 不得执行带发布凭据的作者代码；运行环境/日志/生成文件无 token；工具预演与执行权限可区分 |
| C-17 | 首发和全量回归 | npm run verify 全部通过、无 cancelled，构建确定性；四款首发安装/启动/暂停/存档/Continue 和现有 UI 不回归 |
| C-18 | 开发包呈现 | 新投稿按全出血/顶部 112px/右下 96×96 规则验收；真实游戏内部推进，不仅 Runtime 外壳通过 |
| C-19 | Skill 可获取且可移植 | 分发目录/归档可用，版本和工具获取方式明确；仓库外调用无需维护者路径、私有 Skill 或平台内部知识 |
| C-20 | Skill 实际开发能力 | 仅给玩法需求与 Skill，AI 产出真实可玩、符合 manifest/SDK/呈现规范的源码和安装包；Vanilla/React 构建校验均通过 |
| C-21 | Skill 纠错和证据 | 非法包案例被修复并重验；真实行为和环境边界记录准确，不关闭校验或伪造成功 |
| C-22 | Skill 更新与权限边界 | 1.0.0 → 1.0.1 旧存档可恢复；缺素材/身份/环境如实报告；未获授权不外发投稿或操作生产市场 |

自动测试用受控 mock/fixture 覆盖错误分支；证据需标明模拟/真实。公网、人工试玩和 CI 权限配置不能由单元测试替代。

M4 至少用一个由开发者 Skill 指导 AI 完成的非首发新 ID，发布 1.0.0、更新 1.0.1、再撤下目录；验证没有改动用户日常 DSH profile。样例需明确为测试游戏，生产市场是否保留由用户决定。

## 13. 上线准备与开发者交付物

开发者最终应交付：

- 平台功能 PR，相关契约、模板、测试和重建产物齐全；不自行合并/打 tag。
- 内容仓库模板和完整初始化说明；已获授权时提供真实仓库/配置状态，未获授权则给出精确缺项。
- 可分发的 `skills/dsh-game-developer/` 及其版本/兼容说明、工具获取与实际调用方法；提供独立 AI 使用评估的输入、输出、命令和行为证据。
- 作者用 `docs/community-submission.md`：从安装/读取 Skill、表达玩法需求、开发、提交、修正到更新，不需要阅读平台源码才能交包。
- 维护者用 `docs/community-operations.md`：从打开投稿到运行上架命令、合并 PR、用户确认，包含失败重试、撤下及权限准备。
- `docs/verification/community-publishing/`：测试结果、模拟 API 矩阵、真实公网链路、目录 PR/Release 链接、截图、SHA、未验证项。
- 交接说明：分支与 commit、改动、实际测试数量、外部仓库状态、配置迁移、剩余风险。

上线前用户/仓库 Owner 需要确认的外部配置：目标内容仓库 owner/name、可用的 PR/分支保护设置、Release 不可变策略、维护者 GitHub CLI 权限、真实线上索引地址。此处不能由软件单测证明；没有完成就写“待配置/待验证”。

交 Codex review 时必须能回答：

1. 我收到一份真实投稿，下一条具体运行什么命令？
2. 工具在哪里要求人工批准，批准究竟绑定哪份包与素材？
3. 合并哪个 PR 才算上架？失败时为何不会改变现有市场？
4. 一个已安装插件的普通用户需要做什么，多久能看到？
5. 作者换包、删仓库、重复提交、两个更新同时来，会发生什么？
6. GitHub 不可达时，新用户和已有用户各看到什么？
7. 外部开发者只把玩法需求和 Skill 交给 AI，具体如何拿到可安装包？哪些环节实际验证过，哪些仍需维护者审查？

完成判定以实际 Skill 指导 AI 开发→打包→投稿→验收→归档→目录 PR→公网刷新→安装→更新→撤下的证据为准；不能用“CI 全绿”或“教程已写”代替整条链路完成。
