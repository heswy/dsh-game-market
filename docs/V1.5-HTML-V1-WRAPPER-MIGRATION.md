# html-v1 的 wrapper 化：迁移建议（M2 提案，未实施）

> 状态：**提案，待 Codex 裁决**。M2 **不**改变 `html-v1` 的服务路径。
> 关联：`docs/V1.5-CONTRACTS.md` §7.5 / §7.5.1 / §7.5.2、`docs/verification/v1.5/resources.md` §5.4（CR-P1）、
> M1 验收矩阵 §8 第 1 条（已知残余项）。
>
> 记录日期：2026-10-20，基线 `origin/main` `9388b37`（M1 已合入）。

## 1. 现状与缺口

| 格式 | 入口文档来源 | Runtime 的 iframe | 是否可被 wrapper 阻断自导航 |
|---|---|---|---|
| `asset-zip-v2` | **资源 origin**（`/res/<instance>/<token>/<entry>`） | 外层 wrapper（不加 sandbox）+ 内层游戏 iframe（`sandbox="allow-scripts"`） | **是**（wrapper 的 `frame-src` 只放行 resourceOrigin，§7.5.1/§7.5.2） |
| `html-v1` | **DSH origin**（`/api/game-market/entry?...`） | 单层 iframe（`sandbox="allow-scripts"`），`sandbox` 让文档变 opaque origin | **否** |

`html-v1` 仍然存在 M0 CR-P1 复现的那条边界缺口：游戏文档执行
`window.location.replace('https://…')` 时**目标服务真的会收到请求**——游戏文档自身的 CSP 约束不了自己的导航，
而 DSH 页面本身没有 `frame-src`，Runtime 也没有 wrapper 可放。

M1 的记录口径一直是「**M1 只为 `asset-zip-v2` 引入 wrapper；`html-v1` 保持 V1 路径，其残余自导航风险为已知项**」，
并在 M1 验收矩阵 §8.1 与契约 §15.3 明确列出。**M2 不改变这一点**，本文件只是把后续迁移选项写清楚交裁决。

## 2. 为什么不能简单「给 html-v1 也套现有 wrapper」

现有 wrapper 只允许内嵌**它自己 origin**（resource origin）上的文档：

```
Content-Security-Policy: frame-src <resourceOrigin>; child-src <resourceOrigin>
```

而 `html-v1` 的入口文档在 **DSH origin**（`/api/game-market/entry`）。两种直接做法都有问题：

- **放宽 wrapper 的 `frame-src` 到 DSH origin**：wrapper 会变成「可内嵌 DSH 应用」的跳板，
  DSH 页面里任何脚本都能借它内嵌自己的界面（点击劫持面扩大），且 wrapper 的 CSP 语义从
  「只允许资源 origin」退化成「允许两个 origin」，值不回票价。
- **只给 html-v1 的入口文档加 `frame-ancestors`**：`frame-ancestors` 只能限制**谁能嵌它**，
  不能限制它自己导航（这正是 CR-P1 的结论），所以对缺口无效。

结论：**wrapper 只能内嵌资源 origin 上的文档**，要让 html-v1 受 wrapper 保护，必须先让 html-v1 的入口文档
**从资源 origin 提供**。

## 3. 候选方案

### 方案 A（推荐）：html-v1 入口也由资源 origin 提供，复用同一 wrapper

- 安装/内置的 `html-v1` 包在启动时，资源服务为实例登记一个**单文件清单**：`files = [entry.html]`，
  与 `asset-zip-v2` 走同一套 `/res/<instance>/<token>/<path>` 地址与实例凭证（一次性 launch、renew/release/TTL 全部复用）。
- `LaunchInfo` 对 `html-v1` 追加 `resourceOrigin`/`resourceBase`/`entryResourceUrl`/`wrapperUrl`/`wrapperResourceUrl`，
  **同时保留 V1 的 `entryUrl`（DSH `/api/entry`）**：新 Runtime 用 wrapper 字段，旧 Runtime 继续用 `entryUrl`（向后兼容）。
- html-v1 入口文档在资源 origin 上使用**V1 的 CSP 指令集**（`script-src/style-src 'unsafe-inline'`、`img-src data:`、
  `connect-src 'none'` + 外发边界全 `'none'`），但 `frame-ancestors` 覆盖整条祖先链：`<DSH origin> <resourceOrigin>`。
- Runtime 对两种格式统一走 wrapper（`LaunchInfo.useWrapper = true`），`sandbox="allow-scripts"` 由 wrapper 内层游戏 iframe 施加。

**代价**：`html-v1` 的入口文档多一次本地 HTTP 往返（同机 loopback，实测可忽略）；
`/api/game-market/entry` 仍需保留并继续工作（旧客户端 + 兼容），即两条入口并存。

**风险与验证要求**：
1. `html-v1` 单文件游戏大量使用内联 `<script>`/`<style>` → 资源 origin 的 CSP 必须保留 V1 的 `'unsafe-inline'`
   与 `img-src data:`（不能套用 `asset-zip-v2` 的严格 CSP）；
2. 旧 Runtime（无 wrapper 字段）必须继续工作——用 M1 的「旧 LaunchInfo 回退」用例覆盖；
3. `/api/entry` 的一次性凭证语义不变（不能因为增加资源 origin 入口而放宽）；
4. 需要用真实浏览器重跑 CR-P1 的 C1/C2/C3/C4 矩阵，**html-v1 的 C1（无 CSP 页）必须从泄漏变为阻断**，
   且要有「游戏正常运行 + 目标端零请求」的正向对照，否则会重演 M0 的假通过。

### 方案 B：只在 DSH 页面层加 `frame-src`

需要 DSH 宿主配合（页面级 CSP），本项目不能单方面保证；且跨宿主版本不可控。
**不建议作为主方案**，但若上游愿意提供，可与 A 叠加（纵深防御）。

### 方案 C：维持现状 + 强化检测

保留 `/api/entry` 单层 iframe，仅依赖 Runtime 的导航/心跳检测（`GM-5012`/`GM-5013`）在事发后撤销能力。
**这只是止损**：请求已经发出，数据可能已离开，不构成阻断。

## 4. 建议

1. **M2/M3 期间保持现状**（方案 C 的检测保留），不静默改变 `html-v1` 行为；
2. 若 Codex 同意，**M4/M5 用方案 A** 迁移，并在同一 PR 内：
   - 资源服务支持 html-v1 单文件实例；
   - Runtime 统一 wrapper（保留 `entryUrl` 兼容）；
   - 重跑 CR-P1 四用例 + 旧 Runtime 兼容用例；
   - 更新契约 §7.5/§7.5.1（把「仅 asset-zip-v2」改为「所有格式」，并记录 html-v1 的 CSP 差异）；
   - 更新验收矩阵，把 §8.1 的已知项关闭。

## 5. 本提案**不**包含

- 不改 `html-v1` 的任何既有行为（服务路径、CSP、`entryUrl` 语义、安装/存档）；
- 不改契约正文（§7.5 仍按 M1 口径：wrapper 只约束 `asset-zip-v2`）；
- 不宣称「所有格式均已实现包外导航阻断」——**当前只有 `asset-zip-v2` 有**。

## 6. 交给 Codex 的问题

1. 方案 A 是否可接受？特别是「html-v1 在资源 origin 上保留 `'unsafe-inline'`」这一点是否可接受
   （否则现有全部 html-v1 游戏会失效）。
2. 迁移应放在 M4/M5，还是必须更早？
3. 是否需要先补一个**隔离探针**（在真实 DSH 页面里，用方案 A 的形态验证 html-v1 能被 wrapper 阻断且游戏照常运行），
   再决定是否进入实现？
